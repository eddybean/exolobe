Exolobe 概要 仕様 アーキテクチャ 意思決定記録

アーキテクチャ

中心にあるのは「ユースケースが外の世界を何も知らない」という一点です。 whisper も llama.cpp も Electron も、すべて外側の交換可能な部品として扱います。

層構造と依存の向き

依存は常に内向きです。domain は何にも依存せず、application は domain と自分が定義したインターフェース（ポート）だけを知ります。 実装は外側にあり、内側の型に合わせて作られます。

層場所知っていること知らないこと
Entities src/domain 録音の状態遷移、文字起こしのマージ規則、設定の妥当性 ファイル、プロセス、ネットワーク、フレームワーク
Use Cases src/application domain と ports/ のインターフェース whisper、llama.cpp、Electron、ファイル形式
Interface Adapters src/infrastructure 外部ツールの呼び出し方、ファイル形式、HTTP UI、IPC、アプリのライフサイクル
Frameworks src/main, src/preload, src/renderer Electron、React、IPC 業務ルール（すべて内側に委ねる）

録音のプロセス構成

マイクとシステム音声は取得経路が異なります。マイクは getUserMedia が レンダラー側の API であるためレンダラーで取り、システム音声は main が Core Audio Tap から 直接受け取ります。

システム音声は await できないイベントコールバックで届きます。素朴に fire-and-forget で書き込むと、停止時に未完了の書き込みが取りこぼされて音声が欠落します （実際にテストがこの不具合を検出しました）。書き込みはプロミス鎖で直列化し、 停止前に必ず流し切っています。

停止後のパイプライン

ステップ同士は成果物ファイルを介してのみつながります。次のステップは前の ステップの戻り値ではなく、ディスク上のファイルを読みます。これにより個別リトライが 特別な仕組みなしに成立します。

状態の持ち方

  • 各ステップは pending / running / done / failed のいずれかを持ちます。
  • ステップ開始時点でも保存します。途中でアプリが落ちても「実行中で止まった」と分かります。
  • 録音全体の状態はステップ群から導出します。実行中が最優先、次に失敗、最後に完了です。
  • 中間 WAV は全ステップが揃うまで消しません。リトライで再利用するためです。

プロセス分離

推論は utilityProcess に隔離しています。llama.cpp と sherpa-onnx は数 GB の メモリを使うネイティブコードで、main プロセスで動かすとネイティブ側のクラッシュが ウィンドウごとアプリを落とすためです。

プロセス担当落ちたときの影響
Main 録音、ファイル、IPC、トレイ アプリ全体が終了する
Renderer UI、マイク取得 画面が再読み込みされる。録音は main 側で継続
utilityProcess（パイプライン） ミックス、文字起こし、話者識別、要約、エンコード 処理中のジョブは失われるが、録音済みファイルと状態はディスクに残る。 次の依頼でワーカーを作り直す
utilityProcess（意味検索） 意味検索の索引作成とクエリの埋め込み。3 分使われなければ終了 検索と索引作成が失敗するだけ。索引は再生成できる
子プロセス audiotee、whisper-cli、afconvert 該当ステップのみ失敗する

ワーカーは Electron API を持たない Node 環境で動くため、electron を import しません。 必要なパス（userData、同梱リソース）は環境変数で渡しています。ジョブは 1 件ずつ 直列に処理します。whisper と LLM を同時にメモリへ載せると 16GB では足りないためです。

意味検索のワーカーは別に立てます（ADR-029）。パイプラインの列に 並ぶと要約の間ずっと検索が待たされ、1 回ごとに作り直すとモデルの読み込みで検索のたびに数秒かかるためです。 パイプラインが動き出したら索引の同期を止めてワーカーを終わらせ、要約とメモリを取り合わないようにします。 結線は search-container.ts の 1 か所です。

main と renderer の境界

contextIsolation は有効のままで、renderer は ipcRenderer にも Node API にも 触れません。preload が型付きの API だけを公開します。境界を越えるデータは Date や クラスインスタンスを避け、プリミティブと素のオブジェクト（DTO）だけで表します。

renderer から届く値は信頼できないため、各 IPC ハンドラの入口で型を絞ってからユースケースへ 渡します。例外はそのまま返すと Error invoking remote method に包まれて読めなくなるので、 利用者向けメッセージだけを持つ Error に詰め替えています。

テスト

TDD で先にテストを書く方針です。ポートを Fake に差し替えれば、ユースケースはサーバーも DB も 起動せずに完全に検証できます。

層テストの中心I/O
domain 状態遷移、マージ規則、話者割り当て、バリデーション なし
application ユースケースの振る舞い、失敗の切り分け、リトライ なし（Fake ポート）
infrastructure WAV ヘッダ、整列とクリッピング、whisper 出力の解析、再開可能な取得 一時ディレクトリ、実 afconvert
統合 録音から保存までを本番と同じ実装で通す（推論のみ差し替え） 実ファイル、実 afconvert

現在 208 件。テストが実際に検出した不具合には、録音の書き込み競合による 音声欠落があります。

差し替えの手順

各バックエンドはポートの裏にあるため、置き換えは局所的です。

差し替えたいものポート触る場所
文字起こし（例: クラウド API） TranscriptionPort 実装を 1 つ追加し、pipeline-container.ts の分岐に足す
要約 SummarizationPort 同上
話者識別 DiarizationPort 同上（無効時は NullDiarizer）
音声取得 SystemAudioSource container.ts の 1 行
保存形式 RecordingRepositoryPort / RecordingArtifactPort container.ts の 2 行

いずれの場合も src/domain と src/application は変更しません。
