ADR-001 デスクトップ音声の取得方式

ADR-001

Core Audio Process Tap でシステム出力を複製する

背景

当初の要望は「仮想デバイスを用いず、画面の録画機能などでデスクトップ音声をキャプチャしたい」 でした。仮想デバイス不要という条件は満たせますが、画面録画 API が最善とは限りません。

選択肢

方式判定理由
BlackHole 等の仮想オーディオデバイス 不採用 要望により除外。利用者に別途インストールと出力先の切り替えを強いる
ScreenCaptureKit（SCStream.capturesAudio） 不採用 「画面収録」権限が必要で紫のインジケータが常時点灯する。映像処理のオーバーヘッドを伴う。 ポストミキサー録音のためシステム音量を下げると録音音量も下がる
Electron getDisplayMedia の loopback audio 不採用 macOS では Chromium の内部フラグ依存で不安定。Electron 39 で CoreAudio Tap が デフォルト化されるなど破壊的変更が続いており、不具合報告も多い
Core Audio Process Tap（macOS 14.2+） 採用 下記

採用した理由

観点Core Audio TapScreenCaptureKit
権限オーディオ録音のみ画面収録
収録インジケータ出ない紫のインジケータが点灯
システム音量の影響受けない（プリミキサー）追従する
映像処理なしあり
権限付与後の再起動不要求められることが多い
結論。要望の本質は「仮想デバイスを入れさせないこと」であり、画面録画 API は そのための手段の一案にすぎませんでした。Core Audio Tap は同じ目的をより低い権限で、 より良い音質で達成します。実装は npm パッケージ audiotee（Swift バイナリの薄いラッパー）を 使い、Electron に同梱すると親アプリの署名を継承します。

受け入れた制約

  • macOS 14.2 以上が必須になる。
  • 既定の出力デバイスからしか取得できない。会議中の出力先変更には追従しない。
  • 権限の性質上、署名済みバイナリでなければ動かない（→ ADR-014）。

ADR-002 アプリの実装スタック

ADR-002

Electron + React を採用し、ネイティブ SwiftUI を見送る

選択肢

案判定評価
ネイティブ SwiftUI 不採用 軽量・省電力・OS 統合は最良。macOS 26 の SpeechAnalyzer によるオンデバイス 日本語文字起こしも使える。一方で UI と ML 周辺の実装コストが高く、 推論エコシステム（whisper.cpp / llama.cpp / sherpa-onnx）の Node 連携が使えない
Electron + React 採用 UI の実装が速い。音声キャプチャは小さな Swift バイナリを子プロセスとして 同梱すれば足りる。推論ライブラリの Node バインディングがそのまま使える

受け入れた代償

  • アプリサイズが約 142MB。
  • メモリ使用量がネイティブより多い。
  • OS の新 API（SpeechAnalyzer 等）をすぐには使えない。

将来ネイティブへ移行する場合でも、業務ルールは src/domain と src/application に閉じているため、書き換えの対象は外側の層に限られます。

ADR-003 推論の実行場所

ADR-003

文字起こしも要約も完全にローカルで行う

背景

会議の音声と議事録は機微情報を含みます。処理場所の選択はプライバシーとコストに直結します。

選択肢

案判定評価
クラウド API（Whisper API / Claude API 等） 不採用 精度と要約品質は最高。ただし会議音声そのものが外部へ送信される。従量課金も発生する
ハイブリッド（文字起こしはローカル、要約はクラウド） 不採用 音声は守られるが、議事録の全文が外部へ出る
完全ローカル 採用 音声もテキストも一切外に出ない。オフラインでも動く。従量課金なし
結論。会議録音という用途では、機密性が要約品質より優先されます。 ただし TranscriptionPort と SummarizationPort を分離してあるため、 クラウド実装の追加は後からでも局所的な変更で済みます。

受け入れた代償

  • 要約品質はクラウドの大規模モデルに劣る。
  • 初回に約 5.7GB のモデルダウンロードが必要（→ ADR-011）。
  • 16GB のメモリでは whisper と LLM を同時に載せられず、逐次実行になる。

ADR-004 要約のバックエンド

ADR-004

Ollama をやめて node-llama-cpp をアプリ内に取り込む

背景

当初は Ollama の HTTP API を叩く設計でした。実装の途中で「Ollama に依存せずアプリ内に バンドルできないか」という問いが出たため、再検討しました。

比較

観点Ollamanode-llama-cpp
利用者の事前準備インストールと常駐が必要不要
モデルの入手Ollama が管理アプリが管理（GGUF）
モデルのサイズ約 5GB約 5GB（差なし）
アプリサイズ増えない約 +80MB
メモリ解放自動アンロード明示的な dispose() が必要
失敗の分かりやすさ「起動していない」が頻発アプリ内で完結
結論。モデルのダウンロード量は変わらないため、Ollama の利点は 「アプリサイズが増えないこと」だけでした。それに対し「利用者が別ツールを入れて 常駐させる」という導入時の摩擦は大きく、割に合いません。 @node-llama-cpp/mac-arm64-metal のプリビルドがあることを確認して採用しました。

実装上の注意

  • 16GB では whisper と同時に載せられないため、要約が終わったら必ず dispose() する。
  • ネイティブモジュールなので、パッケージ時に asar から展開する設定が要る。
  • ESM 専用パッケージのため、CJS の main からは動的 import() で読む（→ ADR-012）。

ADR-004b 要約モデル

ADR-004b

Qwen3-8B から Gemma 4 E4B (QAT q4_0) へ変更する

背景

当初の既定は Qwen3-8B でした。日本語に強いモデルとして Gemma 4 E4B の提案があり、 比較した結果こちらを既定にしました。

比較

観点Qwen3-8B Q4_K_MGemma 4 E4B QAT q4_0
コンテキスト長8K128K
ファイルサイズ約 5GB5.15GB
量子化後付け量子化QAT（量子化を考慮した学習）
1 時間の会議分割要約が必要一度に読める
配布元コミュニティGoogle 公式（非 gated を確認済み）
決め手はコンテキスト長です。 分割要約は部分ごとに文脈が切れ、決定事項や担当者を取りこぼしやすくなります。 1 時間規模の会議を一度に読ませられることは、要約品質に直接効きます。 サイズはほぼ同じで容量面の利得はありません（E4B は「実効 4.5B」ですが総パラメータは約 8B）。 日本語の扱いと、q4 での劣化が小さい QAT 版であることも理由です。

付随する変更

既定のコンテキスト長を 8192 から 32768 へ引き上げました。128K すべてを使わないのは、 KV キャッシュがメモリを大きく消費するためです。32K あれば 16kHz の 1 時間の会議は 分割せずに収まります。

ADR-005 音声コーデック

ADR-005

HE-AAC ではなく AAC-LC を既定にする

背景

「ファイル容量を節約するためエンコードして抑えたい」という要望に対し、当初は低ビットレートに 強い HE-AAC（aach）を選びました。実測したところ想定と異なる挙動をしました。

実測

16kHz モノラルの帯域制限ノイズ 60 秒を -b 32000 -s 3 でエンコードした結果:

計測結果 入力 n.wav 1,920,044 bytes (16kHz mono 16bit = 256kbps)
aach out_aach.m4a 79,808 bytes → 10 kbps / コア 8000 Hz
aac out_aac.m4a 239,487 bytes → 31 kbps / 16000 Hz
HE-AAC は指定ビットレートを無視していました。 -b 32000 を与えてもコアを 8kHz・約 10kbps まで落とします。容量は 1/3 になりますが、 会議音声の明瞭さと、後から再度文字起こしできる余地を損ないます。AAC-LC は 16kHz と 指定ビットレートを維持し、1 時間あたり約 14MB に収まります。これは十分に小さく、 容量のために品質を犠牲にする理由がありません。

扱い

  • 既定は AAC-LC。設定で HE-AAC も選べる（最小サイズを優先したい場合のため）。
  • この挙動はテストで固定してあり、既定を戻す変更は失敗する。
  • ffmpeg は同梱しない。macOS 標準の afconvert で足りるため。

ADR-006 話者識別の方式

ADR-006

トラック分離を土台にし、クラスタリングは任意で重ねる

選択肢

案判定評価
混合音声にフルダイアライゼーション 不採用 精度が環境依存で誤りが出やすい。自分の声まで推論対象になり、確実に分かる情報を捨てている
2 話者分離のみ 不採用 実装は単純で 100% 正確だが、相手が複数人でも 1 人扱いになる
段階実装 採用 下記

設計

マイクとシステム音声を別トラックで録るため、「自分」と「相手」は推論なしで確定します。 その上で、相手トラックにだけ sherpa-onnx のクラスタリングを掛けて「参加者A / B / C …」へ 細分化します。自分のトラックを推論に掛けないぶん、精度と処理時間の両方で有利になります。

副次的な利点

  • 文字起こしをトラックごとに実行するため、クロストークの影響を受けない。
  • クラスタリングが失敗しても、2 話者分離のまま処理を続行できる（NullDiarizer）。
  • 話者名は詳細画面で手動変更できる。推論の誤りを利用者が直せる。

話者数の上限

sherpa-onnx の閾値クラスタリングは話者数を指定できず、雑音や短い相槌で実際より多くの クラスタを作ります。発話時間の合計が長い話者から上限まで残し、あふれた分のターンは捨てます。 捨てられた区間は汎用の「参加者」ラベルに戻ります。

ADR-007 whisper バイナリの配布

ADR-007

パッケージ時にビルドして同梱する

背景

モデルファイルはアプリ内でダウンロードできますが、whisper-cli は実行バイナリです。 配布版の利用者に Homebrew を要求したくありません。

調査結果

whisper.cpp の最新リリース資産を確認しました。

whisper.cpp リリース資産 whisper-b4938-xcframework.zip 53.6 MB ← ライブラリ（CLI ではない）
whisper-bin-ubuntu-arm64.tar.gz 4.6 MB
whisper-bin-ubuntu-x64.tar.gz 9.5 MB
whisper-bin-Win32.zip 5.3 MB
whisper-bin-x64.zip 8.4 MB
（macOS 向けの CLI バイナリは存在しない）
ダウンロードでは解決できません。 scripts/build-whisper.sh がパッケージ時に whisper.cpp を Metal 有効・静的リンクで ビルドし、resources/bin/whisper-cli として同梱します。

実行時の解決順

  1. 設定に書かれたパス（既定値 whisper-cli 以外のとき）
  2. 同梱バイナリ（パッケージ済みアプリのとき）
  3. PATH 上の whisper-cli（開発時）

設定を最優先にしているのは、手元でビルドした版や別バージョンを使いたいケースを 塞がないためです。

ADR-008 パイプラインの実行場所

ADR-008

推論を utilityProcess に隔離する

理由

llama.cpp と sherpa-onnx は数 GB のメモリを使うネイティブコードです。main プロセスで 動かすと、ネイティブ側のクラッシュがウィンドウごとアプリを落とします。録音済みの データを扱うアプリでこれは受け入れられません。

隔離の効果。ワーカーが落ちても main は生き残り、録音済みファイルと 各ステップの状態はディスクに残ります。利用者には「処理プロセスが終了しました」と伝え、 詳細画面から失敗したステップを再実行できます。

設計上の制約

  • ワーカーは Electron API を持たない Node 環境で動くため electron を import できない。 必要なパスは環境変数で渡す。
  • ジョブは 1 件ずつ直列に処理する。whisper と LLM を同時に載せると 16GB では足りない。
  • ワーカーは必要になったときに起動し、落ちたら次の依頼で作り直す。

ADR-009 文字起こしのタイミング

ADR-009

録音中は推論せず、停止後にまとめて処理する

案判定評価
リアルタイム字幕＋後処理 見送り UX は良いが実装量が大きく、会議中の発熱・電池消費が増える。 会議アプリと CPU を奪い合うリスクもある
停止後にバックグラウンド処理 採用 録音中は軽量な書き込みのみ。精度が高く、実装もシンプル

録音中に行うのは PCM のディスク書き込みだけです。会議そのものを妨げないことを優先しました。 リアルタイム字幕は将来の追加候補として残しています。

ADR-010 ステップ失敗時の扱い

ADR-010

失敗は依存するステップだけを止める

選択肢

案判定評価
1 つでも失敗したら全体を中止 不採用 要約に失敗しただけで音声すら残らない。最も価値の高い成果物を失う
失敗を無視して続行 不採用 文字起こしが無いのに要約を試みるなど、無意味な処理と分かりにくいエラーを生む
依存関係を宣言して部分的に止める 採用 下記

効果

  • 要約が失敗しても、音声のミックスとエンコードは完了する。
  • 文字起こしが失敗したら、話者識別と要約はスキップして理由を記録する。
  • ステップは成果物ファイル経由でのみつながるため、個別リトライが自然に成立する。
  • 中間 WAV は全ステップが揃うまで消さない。リトライで再利用するため。

ADR-011 モデルの入手経路

ADR-011

アプリ内でダウンロードし、設定へ自動反映する

背景

当初はセットアップスクリプトで Homebrew とモデルを導入する前提でした。配布版の利用者に ターミナル操作を求めるのは現実的ではありません。

設計

数 GB のファイルを扱うため、次の 3 点を守っています。

方針理由
完了するまで最終パスに置かない 中断で壊れたモデルを掴ませない。読み込み時に分かりにくいエラーになるため
Range 要求で再開する 不安定な回線で 5GB を最初からやり直させない。中断時も受信済みバイトは書き込んでから止める
sha256 を検証する 壊れていれば途中ファイルごと破棄する。残すと再開のたびに同じ失敗を繰り返すため

確認したこと

  • Google の Hugging Face リポジトリはライセンス同意で gate されていることが多いため、対象が非 gated であることを確認した。
  • チェックサムは実際のレスポンスヘッダから取得した実測値を埋め込んでいる。
モデルが無くても録音は始められます。 必須にしているのは保存先の選択だけです。先に会議を録っておき、後から文字起こしと 要約を実行できます。5.7GB のダウンロードを待たせてから会議に臨ませる設計にはしません。

モデルは録音の保存先ではなくアプリのデータディレクトリに置きます。 モデルは会議の成果物ではなく再取得できるキャッシュであり、利用者の保存先を 圧迫させないためです。

ADR-012 main / preload のモジュール形式

ADR-012

electron-vite の既定である CJS を使う

経緯

当初 "type": "module" で ESM 出力にしたところ起動に失敗し、 「Electron の ESM main では electron の名前付きインポートが解決できない」と 判断して CJS へ切り替えました。

この判断理由は誤りでした。 実際の原因は、検証に使ったシェルに ELECTRON_RUN_AS_NODE=1 が設定されており、 Electron が素の Node として起動していたことです。環境変数を解除した状態では ESM main でも import { app } from 'electron' は正常に解決されます。

それでも CJS のままにした理由

  • electron-vite の既定であり、最も広く使われている構成である。
  • ESM 専用の audiotee と node-llama-cpp は動的 import() で読める。CJS 出力でも import() は require に変換されない。
  • 既定から外れることで得られる利点が無い。

起動しないときは ELECTRON_RUN_AS_NODE を確認してください。 この環境変数が設定されていると、Electron は GUI を起動せず require('electron') が API を返しません。

ADR-013 アプリ名

ADR-013

実行ファイル名は ASCII、表示名だけ日本語にする

発見した不具合

productName: 会議レコーダー でパッケージすると、生成されたアプリが 起動直後に SIGTRAP で落ちました。ログもクラッシュレポートも出ません。

切り分け

検証結果
署名を外すSIGKILL（arm64 は署名必須のため当然）
--deep で署名し直すSIGTRAP のまま
hardened runtime を外すSIGTRAP のまま
同じ app.asar を開発版 Electron で実行正常に起動（＝アプリのコードは無実）
productName を ASCII に変更正常に起動
原因は日本語の productName でした。 実行ファイル名・ヘルパーアプリ名・フレームワーク参照がすべてこの名前から生成されるためです。 productName を Meeting Recorder に戻し、利用者に見える名前は CFBundleDisplayName で日本語にしました。Finder やメニューバーでは 従来どおり「会議レコーダー」と表示されます。

Release 資産のファイル名も artifactName で ASCII に固定しています。 日本語のままだと URL がパーセントエンコードされて扱いにくくなるためです。

ADR-014 配布時のコード署名

ADR-014

証明書が無くても ad-hoc 署名は必ず行う

制約

NSAudioCaptureUsageDescription による権限は署名済みバイナリでしか 有効になりません。無署名で配布すると、アプリは起動してもシステム音声が取得できず、 しかも原因が分かりにくい形で失敗します。

案判定結果
署名しない 不採用 機能しないアプリになる。選択肢として成立しない

ADR-015 一覧データの持ち方

ADR-015

meta.json を正とし、index.json はキャッシュとして扱う

背景

保存先は利用者のディレクトリです。Finder で移動されたり、他のツールで整理されたり、 バックアップから部分的に復元されたりします。単一のインデックスファイルに依存すると、 その一箇所が壊れただけで一覧が消えます。

結論。各録音ディレクトリの meta.json を正とし、 ルートの index.json は一覧表示を速くするためのキャッシュに留めます。 index.json が失われても壊れていても、meta.json から一覧を再構築します。

あわせて守っていること

  • 書き込みは一時ファイル経由の置換で行う。中断しても壊れたファイルを残さない。
  • 保存済み JSON は既定値へマージして読む。設定項目が増えても古いファイルが使える。
  • 壊れた JSON は「まだ無い」として扱い、起動を止めない。
  • 保存先が未設定でも一覧はエラーにせず空を返す。初期設定画面より先にエラーを出さないため。

ADR-016 同梱バイナリのパス解決

発見した不具合

開発時は動くのに、パッケージ済みアプリでは録音開始が必ず失敗しました。

原因

audiotee は自分の JS の位置からバイナリを探します （__dirname/../bin/audiotee）。パッケージ済みアプリではその JS が asar の 中にあるため、解決されるパスも asar 内になります。asar は OS から見ると 1 つのファイルなので、その中のパスを子プロセスとして起動しようとすると 失敗します。

計測結果（同じバイナリを 2 つのパスで spawn） .../app.asar/node_modules/audiotee/bin/audiotee → NG: ENOTDIR
.../app.asar.unpacked/node_modules/audiotee/bin/audiotee → OK (exit 0)
結論。Electron は fs の呼び出しを unpacked へ透過的に 振り替えますが、child_process.spawn は OS の実ファイルを直接見るため 振り替えが効きません。main プロセス側で unpacked の実パスを解決し、 audiotee に明示的に渡します。開発時は asar を使わないので undefined を渡し、既定の解決に任せます。

対象読み込み方結果
audioteespawn影響あり → 修正
pipeline-worker.jsutilityProcess.forkasar 内から正常に読み込める
ネイティブモジュール（.node）requireElectron が unpacked へ振り替える
whisper-clispawnextraResources なので asar の外にある
afconvertspawnOS 標準（/usr/bin）

エラーメッセージも切り分けました。ENOTDIR / ENOENT は 権限の問題と紛らわしいため、権限エラーとは別の文言で伝えます。

ADR-017 マイクが取れなかったときの録音

ADR-017

録音を止めず、警告を出して継続する

当初の判断と、その誤り

当初は「自分の発話が残らない録音を黙って続けるべきでない」と考え、マイクの取得に 失敗したら録音を停止していました。しかしこれは デスクトップ音声は録れているのに録音そのものを捨てる挙動で、 利用者から見ると停止ボタンが消え、一覧に空のアイテムだけが残ります。

結論。相手の発言が残る録音には十分な価値があります。マイクが 取れなくても録音は継続し、自分の発言が入らないことは録音中ずっと出続ける 警告として伝えます。閉じられるエラーとは別枠にしているのは、録音が終わるまで 見えている必要があるためです。

区別していること

  • マイクの失敗 — 録音は続く。警告のみ。
  • 録音自体の失敗 — 何も録れていないので例外。一覧にも残さない。

失敗の理由も言い分ける

当初はマイクの失敗をすべて「権限を許可してください」と案内していました。しかし マイクが 1 つも接続されていない場合、そのアプリは「システム設定 > プライバシーとセキュリティ > マイク」に現れません。存在しないデバイスへの 権限は要求できないためです。この案内は、現れるはずのない項目を探させてしまいます。

getUserMedia のエラー実際の原因案内
NotFoundError 入力デバイスが無い（Mac mini / Mac Studio には内蔵マイクが無い） 外付けマイクの接続を案内する。設定へは誘導しない
NotAllowedError OS またはブラウザに拒否された プライバシー設定へ誘導する
NotReadableError 他アプリが占有している 他のアプリの確認を促す

エラー名はブラウザ実装によって揺れるため、getUserMedia を呼ぶ前に enumerateDevices() で入力デバイスの有無を確かめ、無い場合は 確実に「接続されていない」として扱います。

この方針は React から切り出した関数に置き、「マイク失敗時に停止を呼ばないこと」を テストで固定しています。同じ退行を繰り返さないためです。

ADR-018 レンダラーの CSP

ADR-018

script-src で blob: だけを追加で許可する

発見した不具合

マイクの権限を許可した直後に The user aborted a request. とだけ表示され、マイク入力が録音されない 状態になっていました。権限は通っているのに原因が分からない、最も追いにくい形の失敗です。

原因

マイクの取り込みには AudioWorklet を使い、そのモジュールを Blob URL から 読み込んでいます。当初の CSP は default-src 'self' だけだったため blob: が許可されておらず、addModule() がブロックされていました。 このとき Chromium は理由を示さず、AbortError の既定メッセージだけを返します。

計測結果（Electron で CSP を変えて addModule を試行） default-src 'self' のみ → NG AbortError "The user aborted a request."
script-src に blob: を追加 → OK
CSP ほぼ無制限 → OK
結論。script-src 'self' blob: を追加します。 default-src は 'self' のままに保ち、リモートのスクリプト読み込みは 引き続き許可しません。Blob URL は同一オリジン由来で、レンダラーは外部コンテンツを 読み込まず contextIsolation も有効なため、緩和の範囲は限定的です。

ワークレットを別ファイルにしなかった理由

blob: を使わず実ファイルとして配置する案もありますが、パッケージ済みアプリでは レンダラーが file:// から読み込まれるため、パス解決と 'self' の 扱いが開発時と変わります。Blob なら開発時とパッケージ時で挙動が同じで、 配布物に追加のファイルも要りません。

あわせて直したこと

  • この段階の失敗を MicSetupError として区別し、「マイクの音声処理を 初期化できませんでした」と何に失敗したかを明示するようにした。権限やデバイスの 問題と切り分けられる。
  • CSP の内容をテストで固定した。script-src に blob: と 'self' があること、リモート読み込みを許可しないこと、 media-src に file: があることを検証する。

ADR-019 ウィンドウ外からの録音操作

ADR-019

メニューバーアイコンとアプリケーションメニューの二本立てにする

発見した不具合

ドキュメントには「メニューバーから録音・停止できる」と書いていましたが、 実際には何も表示されていませんでした。原因は 2 つあり、 どちらも単独で表示を妨げます。

原因症状
埋め込んだアイコンの PNG が破損していた ヘッダは正しいが画像データが壊れており、Electron 側では isEmpty: true / サイズ 0x0 の空画像になっていた
Tray の参照を保持していなかった 生成した Tray を変数に入れていなかったため GC で回収され、 仮にアイコンが正しくても消える（Electron でよくある落とし穴）
結論。アイコンは円を描く生成器で作り直し、モジュール参照を 保持するようにしました。あわせてアプリケーションメニューにも「録音」を 追加しています。「メニューバー」は画面右上の常駐アイコンとも、アプリ名の 並ぶメニューとも解釈でき、どちらを探しても見つかる方が確実だからです。 ⌘R で開始、⌘. で停止できます。

再発を防ぐためにしたこと

  • アイコンの base64 を独立モジュールに切り出し、PNG として妥当か （署名・寸法・展開できること・透明なだけでないこと・RGB が黒であること）を テストで検証する。手で作った値を貼るとヘッダだけ正しい壊れた画像を 埋め込みかねないため。
  • 録音状態の変化を TransportController から購読できるようにし、 メニューとトレイの表示を追従させる。以前はトレイのクリック時にしか更新しておらず、 ウィンドウ側で停止すると表示が古いままになっていた。

ADR-020 無音区間の文字起こし

ADR-020

whisper の VAD で発話区間だけを渡す

発見した不具合

文字起こしに 「ご視聴ありがとうございました」が頻繁に混ざるという 報告がありました。マイクトラックは会議中ずっと録り続けており、自分が喋るのは 全体の 2 割程度です。残りの無音を whisper に通すと、言語モデルとしての性質から 学習データ（YouTube 字幕）に多い定型句が生成されます。 相手トラックにも同じことが起きます。

手元で再現させた結果がこれです。10 秒の微小ノイズ、発話、20 秒の微小ノイズを 繋いだ音声を渡すと、発話していない 30 秒目に文章が現れました。 

[     0- 12280ms] 来週の予定を確認します
[ 30000- 32360ms] ご視聴ありがとうございました

選択肢

方式判定理由
自前のエネルギーベース VAD で前段フィルタ 不採用 追加のモデル配布は不要だが、しきい値の調整が環境依存になる。 発話区間を切り出したあとタイムスタンプを元の時間軸へ戻す処理も自前で持つことになる
whisper へ全体を渡し、無音区間に載ったセグメントを後段で捨てる 不採用 ハルシネーションの発生自体は止められず、無音に対する推論時間も従来どおり掛かる
whisper.cpp の --vad（Silero VAD） 採用 下記
結論。whisper.cpp を v1.7.4 から v1.9.3 へ更新し、 --vad --vad-model で Silero VAD を有効にしました。VAD モデルは 0.9MB と極小なので、モデルカタログに必須として加えています。 同じ音声で試すと、ハルシネーションは消え、発話区間の時刻も 9990-12250ms と正確になりました （VAD 無しでは 0-12280ms と誤っていた）。 タイムスタンプは whisper.cpp が元の音声の時間軸へ戻すため、こちらでの変換は不要です。

併せて入れた二段構え

  • --suppress-nst で非発話トークンを抑制する。VAD をすり抜けた 雑音の分に効く。
  • 既知の定型句（「ご視聴ありがとうございました」など）を、 セグメント全体が完全一致したときだけ落とす。部分一致で消すと 「資料の共有ありがとうございました」のような本物の発言まで失われるため。

壊さないための逃げ道

  • VAD モデルが未取得・削除済み、または設定で無効にされていれば --vad を渡さない。従来どおり文字起こしは動きます。 ADR-006 の話者分割モデルと同じ扱いです。
  • 設定で古い whisper-cli を指している場合に備え、 --vad を知らないバイナリのエラーは 「v1.7.6 以降に更新するか、設定で無効にしてください」という文言へ翻訳する。

残した判断

マイク取得時の autoGainControl は無音時の室内ノイズを持ち上げるため、 この現象を悪化させている可能性があります。ただし声の小さい話者には有利に働くため、 今回は変更していません。

ADR-021 要約の推論バックエンド（MLX 化）

ADR-021

MLX への移行は見送り、GGUF / node-llama-cpp を継続する

背景

このアプリは macOS 専用（arm64）です。Apple 純正の MLX は Apple Silicon 向けに 最適化されており、2026-03-30 には Ollama が Apple Silicon の推論エンジンを MLX へ 切り替えました。「GGUF ではなく MLX 形式にすれば要約が速くなるのではないか」という 問いが出たため、ADR-004 / ADR-004b を再検討しました。

まず確認した前提

確認したこと結果
既定モデル（Gemma 4 E4B）に MLX 版があるか ある。mlx-community/gemma-4-E4B-it-qat-4bit など、 いま使っている QAT 版に対応する変換が公開されている
node-llama-cpp（llama.cpp）が MLX を読めるか 読めない。GGUF と MLX（safetensors + MLX 独自量子化）は 別系統のランタイムで、移行するなら NodeLlamaSessionFactory を丸ごと差し替えることになる

つまり「モデルが無いから不要」という理由では却下できません。判断は 速度の実利と移行コストで決めました。

決め手は、このアプリの推論プロファイルが MLX の苦手側にあること

MLX が llama.cpp の 2〜3 倍という数字は、短いプロンプト × 長い生成 （チャット用途の decode）で出たものです。このアプリの要約は逆の形をしています。

観点チャット用途このアプリの要約
入力数百トークン1 時間の会議 ≒ 32K トークン
出力長い（対話が続く）議事録ぶんだけ（数百〜数千トークン）
支配的なコストdecodeprefill
実行回数連続録音ごとに 1 回（毎回ロードして dispose）

MLX は llama.cpp のスライディングウィンドウキャッシュに対して full prefill 戦略を取るため TTFT で不利になりやすく、30K トークンを超える文脈では Flash Attention を 有効にした llama.cpp より約 50% 遅いという計測が報告されています。 defaultSettings() の contextSize: 32_768 は まさにその領域です（ADR-004b）。

移行コスト

Node から MLX を使う手段判定状況（2026-09 時点）
@frost-beta/mlx 不採用 0.4.0 / 最終公開 2025-04。停滞している
node-mlx 不採用 2.3.0 / 最終公開 2026-01。更新が細い
@mlx-node/lm 不採用 活発だが 0.0.x。Gemma 4 に対応する一方、darwin-arm64 のプリビルドが macOS 26 デプロイターゲットで、旧 OS の利用者を切ることになる
Python + mlx-lm を同梱 不採用 数百 MB 増、署名と notarize の負担。ADR-004 で 捨てたはずの「外部ランタイム依存」に逆戻りする

加えて、MLX 版モデルは別途 4〜5GB のダウンロードになります。 MANAGED_ASSETS が形式ごとの二重管理になり、 ADR-011 の「アプリが入手を引き受ける」体験も複雑になります。

結論。見送ります。 MLX の明確な利得はメモリ使用量が 7〜13% 少ないことですが、これは 「要約が終わったら必ず dispose() する」（ADR-004）で すでに対処済みの問題です。速度については、このアプリが使う長文脈 prefill は MLX がむしろ不利な領域であり、成熟していないバインディングと モデルの二重管理を引き受けてまで得るものがありません。

やるとしたら壊れない形になっている

SummarizationPort → LlmSessionFactory という seam が すでにあるため、移行するときは NodeLlamaSessionFactory の隣に MlxSessionFactory を足し、pipeline-container.ts で summarization.provider により分岐するだけで済みます。 この見送りを理由に、いま seam を先回りして広げることはしません。

MLX 版（mlx-community） 不採用 ADR-021 と同じ理由。Node から MLX を使う経路が成熟していない

ハルシネーションは対処済みで、乗り換え理由にはならない

2026-08 の比較では large-v3-turbo が 1 発話で同じ語句を繰り返し、その 1 件だけで CER 5,525% という異常値を出しています。これは ADR-020 で扱った無音区間のハルシネーションと同じ現象で、 VAD（vad-model）とブロックリストで既に押さえています。 同じ比較でも「既存の Whisper 運用を今すぐ置き換える必要はない」と結論されています。

結論。継続します。 Qwen3-ASR は日本語 WER で 3 ポイントほど上ですが、それを得るには whisper.cpp を捨てて未成熟なランタイムへ移り、 whisper-cli のビルドと同梱（ADR-011）を 作り直すことになります。数ポイントの精度差に対して、 文字起こしという中核機能の足場を丸ごと入れ替えるのは割に合いません。 なお上の数値は第三者ベンチマークであり、会議音声という実際の用途で測ったものでは ありません。乗り換えを本気で検討するときは、自分の録音で測り直すことが前提になります。

量子化の引き上げも見送る

同じ turbo の q5_0 を q8_0 や fp16 へ上げる案もありますが、q5_0 からの WER 改善はごく小さい一方でダウンロードは 574MB から 900MB 前後に増えます。 ADR-011 の「アプリが入手を引き受ける」体験を重くするだけなので採りません。

ADR-023 モデルの削除とアンインストール時のクリーンアップ（2026-09）

ADR-023

設定画面から 1 件ずつ削除できるようにし、アンインストール時の自動クリーンアップは見送る

背景

ADR-011 でアプリがモデルの入手を引き受けるようにした結果、 ~/Library/Application Support/<app>/models/ には合計 6GB 近くが溜まります。 取得する導線はありましたが、減らす導線がありませんでした。 話者分割（任意）を試してやめた場合や、容量を空けたい場合に手立てがない状態です。

削除するのは「アプリが置いたファイル」だけにする

設定には chooseFile で利用者が自分のファイルを指定する逃げ道があります （外付けドライブに置いた大きなモデルなど）。この参照先を消すと、 アプリが管理していない、他の用途と共有しているかもしれないファイルを 消すことになります。そのため FileModelStore.remove() は models/ 配下だけを対象にし、外部パスに対しては設定の参照を外すに留めます。

一方、models/ 配下のファイルは設定が何を指していても消します。 残すと GetModelStatus が既定の保存場所を見て「取得済み」を返し続け、 削除したのに消えていないように見えるためです。 アーカイブ配布のもの（話者分割）は展開先ディレクトリごと消します — model.onnx だけ消しても同梱の付随ファイルが残り、次の取得で残骸と混ざります。

録音中・処理中は断る

ワーカーが読み込んでいる最中のモデルを消すと、ジョブが途中で失敗します （ADR-008 のワーカー隔離があるのでアプリは落ちませんが、 利用者から見れば原因の分からない失敗です）。DeleteModel は status === 'recording' か isProcessing(steps) の録音があれば断ります。 pending が残るだけの録音（リトライ待ち）は動いていないので妨げません — ADR-010 の「失敗しても他は進む」設計上、 未完了の録音はライブラリに残り続けるためです。

アンインストール時の自動クリーンアップは実現できない

macOS で .app をゴミ箱に入れる削除には、 OS 側のフックが一切ありません。インストーラ形式ではないので アンインストールスクリプトを走らせる仕組みもなく、 サンドボックス化していないため（Core Audio Process Tap の権限のため ADR-014 の署名構成を採っている）コンテナの自動削除も働きません。 つまり「アプリの削除を検知して残りを消す」は設計の選択肢ではなく、不可能です。

代替案判定理由
設定画面に「アプリのデータをすべて削除」ボタン 今回は見送り 唯一確実に動く方法だが、個別削除で容量の問題は解消する。まとめて消す要求が実際に出てから作る
DMG にアンインストーラを同梱 不採用 配布物が増え、署名・公証の対象も増える（ADR-014）。得られるのは残骸の削除だけ
常駐プロセスでアプリの存在を監視 不採用 アプリを消した後も何かが残り続けることになり、目的と矛盾する
結論。個別削除だけを入れます。 残るのは models/・settings.json・work/ で、 いずれも ~/Library/Application Support/ 配下という macOS で残骸が置かれる標準の場所です。 会議の成果物は保存先（ADR-015）にあり、 そちらはアプリを消しても残るべきものなので、そもそもクリーンアップの対象ではありません。

ADR-024 メモリ不足時の重い推論（2026-09）

ADR-024

実行前に空きメモリを確認し、足りなければそのステップだけを失敗させる

背景

要約は 5.15GB のモデルを一度にメモリへ載せます。実機で測ったところ、 モデル本体が約 5.69GB、32K のコンテキストが約 1.27GB で、合計およそ 7GB でした （node-llama-cpp の GgufInsights による見積もり）。

これまでのガードは「ジョブを 1 件ずつ直列に処理する」（ADR-008）と 「要約が終わったら必ず dispose() する」（ADR-004）の 2 つでした。 どちらもアプリ内部の同時実行を防ぐだけで、アプリの外の状況は一切見ていません。 16GB の機体で会議アプリとブラウザが 8GB を使っている状態から要約に入ると、 macOS が圧縮とスワップに追われ、会議そのものを巻き添えにします。

不採用にした案

案見送った理由
足りなければコンテキスト長を下げて実行する（縮退） 分割要約は文脈が切れて決定事項を取りこぼす。ADR-004b で コンテキスト長を選択の決め手にしたのに、それを黙って捨てることになる。 品質が落ちたことは利用者に見えない
空くまで待ってから実行する いつ終わるか分からない処理になる。会議直後に議事録を見たい利用者にとって、 「失敗して再実行できる」方が状況を把握しやすい
ダイアログで利用者に確認する 停止後の処理はバックグラウンドで走る（ADR-009）。 そこに同期的な確認を挟むと、席を外している間ずっと止まる
結論。重いステップに入る前に空きメモリを確認し、足りなければ failStep でそのステップだけを失敗として記録します。 ADR-010 の仕組みにそのまま乗るので、要約が止まっても ミックス・文字起こし・エンコードは完走し、音声と文字起こしは残ります。 利用者は他のアプリを閉じてから、詳細画面の「再実行」を押すだけで済みます。

ガードは二重にする

  • 事前チェック（ProcessRecording）。ネイティブコードに 触れる前に止めるので、失敗が確実に「扱えるエラー」になる。
  • 内蔵ガード（node-llama-cpp）。調べたところ ramPadding は指定しなくても既定で RAM の 25%（上限 6GB）、 vramPadding は VRAM の 8%（上限 1.6GB）を確保していました。 つまり内蔵ガードはすでに効いていたので、こちらの役目は 「保守的」のときに締めることだけです。緩める方向には触りません。 既定を下回る値を渡すと締めるどころか緩めてしまうため、必ず大きい方を採ります。

空きメモリの数え方

os.freemem() は macOS では純粋な free ページしか数えず、常に 「空きが無い」と答えます。そこで vm_stat を読みますが、 どのページを空きとみなすかで答えが 2 倍以上変わります。

数え方同一時点での値
free + inactive + speculative + purgeable4.85GiB（30.3%）
総量 − wired − compressor 占有9.72GiB（60.8%）
kern.memorystatus_level（OS 自身の判断）59%
node-llama-cpp の getVramState().free12.71GB
後者を採ります。前者で実装したところ、実際に要約が動く機体で 「標準」が要約を拒みました（空き 4.91GiB / 必要 8.46GiB）。 動く環境で拒む誤検知は、ガードが無いことより悪い結果です。 active・inactive な匿名ページも、大きな要求が来れば macOS が圧縮して回すため、 空きとして数えてよい。この式は OS が jetsam の判断に使う kern.memorystatus_level と 2 ポイント差で一致しており、 OS 自身の見立てに合わせたことになります。

設定

memoryProtection を「保守的 / 標準 / オフ」の 3 段階で持ちます。既定は「標準」。 「オフ」が外すのは事前チェックだけで、node-llama-cpp の内蔵の余白は そのまま残します。外せば OS が固まりやすくなり、この ADR の目的に反するためです。

見積もりの精度について

所要メモリはモデルのファイルサイズとコンテキスト長からの粗い見積もりです。 係数は実機の実測（モデルはファイルの約 1.10 倍、KV キャッシュは約 18.4KB/トークン ＋ 固定 0.62GB）に基づき、安全側へ丸めてあります。モデルを差し替えれば係数はずれますが、 桁を外さない見積もりで目的は足ります。テストは実測値を下回らないことと 実測の 1.3 倍を超えないことの両方で固定しており、 過小（素通り）と過大（誤検知）のどちらにも倒れないようにしています。

ADR-025 録りっぱなしの防止（2026-09）

ADR-025

main プロセスで無音を見張り、続いていたら知らせる。自動では停止しない

背景

会議が終わってもアプリを止め忘れると、無音だけの長い録音が残ります。 止め忘れは後段すべてに響き、文字起こしと要約が無音に対して走り、 メモリと時間を無駄に使います。

見張る場所は main

レンダラーには入力レベルのメーター（readInputLevel）が既にありますが、 そこで見張るとウィンドウを閉じている会議中に効きません。 main にはシステム音声（audiotee）もマイク（pushMicPcm）も集まるため、 両トラックの peak をここで見れば、ウィンドウの有無に関係なく判定できます。 DualTrackRecorder には UI 用の systemLevel() とは別に onPeak の購読を足しました。systemLevel() は読み出しで値を 消費する（メーターを落とすため）ので、同じ口を 2 つの消費者で使うと peak を奪い合います。

自動停止はしない

無音が続いていても、会議が静かなだけかもしれません。意図せず録音が切れる損失は、 止め忘れの損失より大きいので、知らせるだけにとどめます。 応答がなければ同じ間隔で繰り返し知らせるので、通知を見逃しても効果は残ります。

知らせ方は OS 通知（「録音を停止」ボタン付き）とアプリ内の確認バーの両方です。 通知はウィンドウを見ていなくても届き、確認バーは通知を見逃して戻ってきたときに気づけます。

判定は domain の純粋な関数に置く

observeLevel（src/domain/SilenceWatch.ts）は時計もタイマーも持たず、 レベルと時刻を受け取って「知らせるべきか」を返すだけです。main 側の createSilenceMonitor が peak を 1 秒の区間にまとめて渡します。

判定は「1 つでも音があれば数え直す」ではなく「区間のうち何割が無音か」で行います。 前者にすると、会議の後で机に戻ってキーボードを打っているだけで計測が延々と 振り出しに戻り、いつまでも知らせられません。1 秒だけの物音では割合がほとんど動かず 計測は続き、会話が始まれば割合が崩れて数え直しになります。 既定は 5 分・しきい値 0.02（peak）・無音の割合 90%（5 分なら 30 秒ぶんの物音まで許容）で、 時間と有効／無効は設定画面から変えられます。
