ADR-001 デスクトップ音声の取得方式

ADR-001

Core Audio Process Tap でシステム出力を複製する

背景

当初の要望は「仮想デバイスを用いず、画面の録画機能などでデスクトップ音声をキャプチャしたい」 でした。仮想デバイス不要という条件は満たせますが、画面録画 API が最善とは限りません。

選択肢

方式判定理由
BlackHole 等の仮想オーディオデバイス 不採用 要望により除外。利用者に別途インストールと出力先の切り替えを強いる
ScreenCaptureKit（SCStream.capturesAudio） 不採用 「画面収録」権限が必要で紫のインジケータが常時点灯する。映像処理のオーバーヘッドを伴う。 ポストミキサー録音のためシステム音量を下げると録音音量も下がる
Electron getDisplayMedia の loopback audio 不採用 macOS では Chromium の内部フラグ依存で不安定。Electron 39 で CoreAudio Tap が デフォルト化されるなど破壊的変更が続いており、不具合報告も多い
Core Audio Process Tap（macOS 14.2+） 採用 下記

採用した理由

観点Core Audio TapScreenCaptureKit
権限オーディオ録音のみ画面収録
収録インジケータ出ない紫のインジケータが点灯
システム音量の影響受けない（プリミキサー）追従する
映像処理なしあり
権限付与後の再起動不要求められることが多い
結論。要望の本質は「仮想デバイスを入れさせないこと」であり、画面録画 API は そのための手段の一案にすぎませんでした。Core Audio Tap は同じ目的をより低い権限で、 より良い音質で達成します。実装は npm パッケージ audiotee（Swift バイナリの薄いラッパー）を 使い、Electron に同梱すると親アプリの署名を継承します。

受け入れた制約

  • macOS 14.2 以上が必須になる。
  • 既定の出力デバイスからしか取得できない。会議中の出力先変更には追従しない。
  • 権限の性質上、署名済みバイナリでなければ動かない（→ ADR-014）。

ADR-002 アプリの実装スタック

ADR-002

Electron + React を採用し、ネイティブ SwiftUI を見送る

選択肢

案判定評価
ネイティブ SwiftUI 不採用 軽量・省電力・OS 統合は最良。macOS 26 の SpeechAnalyzer によるオンデバイス 日本語文字起こしも使える。一方で UI と ML 周辺の実装コストが高く、 推論エコシステム（whisper.cpp / llama.cpp / sherpa-onnx）の Node 連携が使えない
Electron + React 採用 UI の実装が速い。音声キャプチャは小さな Swift バイナリを子プロセスとして 同梱すれば足りる。推論ライブラリの Node バインディングがそのまま使える

受け入れた代償

  • アプリサイズが約 142MB。
  • メモリ使用量がネイティブより多い。
  • OS の新 API（SpeechAnalyzer 等）をすぐには使えない。

将来ネイティブへ移行する場合でも、業務ルールは src/domain と src/application に閉じているため、書き換えの対象は外側の層に限られます。

ADR-003 推論の実行場所

ADR-003

文字起こしも要約も完全にローカルで行う

背景

会議の音声と議事録は機微情報を含みます。処理場所の選択はプライバシーとコストに直結します。

選択肢

案判定評価
クラウド API（Whisper API / Claude API 等） 不採用 精度と要約品質は最高。ただし会議音声そのものが外部へ送信される。従量課金も発生する
ハイブリッド（文字起こしはローカル、要約はクラウド） 不採用 音声は守られるが、議事録の全文が外部へ出る
完全ローカル 採用 音声もテキストも一切外に出ない。オフラインでも動く。従量課金なし
結論。会議録音という用途では、機密性が要約品質より優先されます。 ただし TranscriptionPort と SummarizationPort を分離してあるため、 クラウド実装の追加は後からでも局所的な変更で済みます。

受け入れた代償

  • 要約品質はクラウドの大規模モデルに劣る。
  • 初回に約 5.7GB のモデルダウンロードが必要（→ ADR-011）。
  • 16GB のメモリでは whisper と LLM を同時に載せられず、逐次実行になる。

ADR-004 要約のバックエンド

ADR-004

Ollama をやめて node-llama-cpp をアプリ内に取り込む

背景

当初は Ollama の HTTP API を叩く設計でした。実装の途中で「Ollama に依存せずアプリ内に バンドルできないか」という問いが出たため、再検討しました。

比較

観点Ollamanode-llama-cpp
利用者の事前準備インストールと常駐が必要不要
モデルの入手Ollama が管理アプリが管理（GGUF）
モデルのサイズ約 5GB約 5GB（差なし）
アプリサイズ増えない約 +80MB
メモリ解放自動アンロード明示的な dispose() が必要
失敗の分かりやすさ「起動していない」が頻発アプリ内で完結
結論。モデルのダウンロード量は変わらないため、Ollama の利点は 「アプリサイズが増えないこと」だけでした。それに対し「利用者が別ツールを入れて 常駐させる」という導入時の摩擦は大きく、割に合いません。 @node-llama-cpp/mac-arm64-metal のプリビルドがあることを確認して採用しました。

実装上の注意

  • 16GB では whisper と同時に載せられないため、要約が終わったら必ず dispose() する。
  • ネイティブモジュールなので、パッケージ時に asar から展開する設定が要る。
  • ESM 専用パッケージのため、CJS の main からは動的 import() で読む（→ ADR-012）。

ADR-004b 要約モデル

ADR-004b

Qwen3-8B から Gemma 4 E4B (QAT q4_0) へ変更する

背景

当初の既定は Qwen3-8B でした。日本語に強いモデルとして Gemma 4 E4B の提案があり、 比較した結果こちらを既定にしました。

比較

観点Qwen3-8B Q4_K_MGemma 4 E4B QAT q4_0
コンテキスト長8K128K
ファイルサイズ約 5GB5.15GB
量子化後付け量子化QAT（量子化を考慮した学習）
1 時間の会議分割要約が必要一度に読める
配布元コミュニティGoogle 公式（非 gated を確認済み）
決め手はコンテキスト長です。 分割要約は部分ごとに文脈が切れ、決定事項や担当者を取りこぼしやすくなります。 1 時間規模の会議を一度に読ませられることは、要約品質に直接効きます。 サイズはほぼ同じで容量面の利得はありません（E4B は「実効 4.5B」ですが総パラメータは約 8B）。 日本語の扱いと、q4 での劣化が小さい QAT 版であることも理由です。

付随する変更

既定のコンテキスト長を 8192 から 32768 へ引き上げました。128K すべてを使わないのは、 KV キャッシュがメモリを大きく消費するためです。32K あれば 16kHz の 1 時間の会議は 分割せずに収まります。

ADR-005 音声コーデック

ADR-005

HE-AAC ではなく AAC-LC を既定にする

背景

「ファイル容量を節約するためエンコードして抑えたい」という要望に対し、当初は低ビットレートに 強い HE-AAC（aach）を選びました。実測したところ想定と異なる挙動をしました。

実測

16kHz モノラルの帯域制限ノイズ 60 秒を -b 32000 -s 3 でエンコードした結果:

計測結果 入力 n.wav 1,920,044 bytes (16kHz mono 16bit = 256kbps)
aach out_aach.m4a 79,808 bytes → 10 kbps / コア 8000 Hz
aac out_aac.m4a 239,487 bytes → 31 kbps / 16000 Hz
HE-AAC は指定ビットレートを無視していました。 -b 32000 を与えてもコアを 8kHz・約 10kbps まで落とします。容量は 1/3 になりますが、 会議音声の明瞭さと、後から再度文字起こしできる余地を損ないます。AAC-LC は 16kHz と 指定ビットレートを維持し、1 時間あたり約 14MB に収まります。これは十分に小さく、 容量のために品質を犠牲にする理由がありません。

扱い

  • 既定は AAC-LC。設定で HE-AAC も選べる（最小サイズを優先したい場合のため）。
  • この挙動はテストで固定してあり、既定を戻す変更は失敗する。
  • ffmpeg は同梱しない。macOS 標準の afconvert で足りるため。 この判断は出力（WAV → m4a）についてのもので、入力側の範囲は ADR-030 で扱う。

ADR-006 話者識別の方式

ADR-006

トラック分離を土台にし、クラスタリングは任意で重ねる

選択肢

案判定評価
混合音声にフルダイアライゼーション 不採用 精度が環境依存で誤りが出やすい。自分の声まで推論対象になり、確実に分かる情報を捨てている
2 話者分離のみ 不採用 実装は単純で 100% 正確だが、相手が複数人でも 1 人扱いになる
段階実装 採用 下記

設計

マイクとシステム音声を別トラックで録るため、「自分」と「相手」は推論なしで確定します。 その上で、相手トラックにだけ sherpa-onnx のクラスタリングを掛けて「参加者A / B / C …」へ 細分化します。自分のトラックを推論に掛けないぶん、精度と処理時間の両方で有利になります。

副次的な利点

  • 文字起こしをトラックごとに実行するため、クロストークの影響を受けない。
  • クラスタリングが失敗しても、2 話者分離のまま処理を続行できる（NullDiarizer）。
  • 話者名は詳細画面で手動変更できる。推論の誤りを利用者が直せる。

話者数の上限

sherpa-onnx の閾値クラスタリングは話者数を指定できず、雑音や短い相槌で実際より多くの クラスタを作ります。発話時間の合計が長い話者から上限まで残し、あふれた分のターンは捨てます。 捨てられた区間は汎用の「参加者」ラベルに戻ります。

ADR-008 パイプラインの実行場所

ADR-008

推論を utilityProcess に隔離する

理由

llama.cpp と sherpa-onnx は数 GB のメモリを使うネイティブコードです。main プロセスで 動かすと、ネイティブ側のクラッシュがウィンドウごとアプリを落とします。録音済みの データを扱うアプリでこれは受け入れられません。

隔離の効果。ワーカーが落ちても main は生き残り、録音済みファイルと 各ステップの状態はディスクに残ります。利用者には「処理プロセスが終了しました」と伝え、 詳細画面から失敗したステップを再実行できます。

設計上の制約

  • ワーカーは Electron API を持たない Node 環境で動くため electron を import できない。 必要なパスは環境変数で渡す。
  • ジョブは 1 件ずつ直列に処理する。whisper と LLM を同時に載せると 16GB では足りない。
  • ワーカーは必要になったときに起動し、落ちたら次の依頼で作り直す。加えて ジョブが片付いたら終了させ、次の依頼では新しいプロセスを起こす。 要約の LLM も話者識別も数 GB を確保するネイティブコードで、解放しても プロセスの占有が完全には戻らない。プロセスごと終わらせるのが確実な返し方であり、 依存の組み立てはジョブごとに行っているので作り直しても失うものは無い （ADR-028）。

ADR-017 マイクが取れなかったときの録音

ADR-017

録音を止めず、警告を出して継続する

当初の判断と、その誤り

当初は「自分の発話が残らない録音を黙って続けるべきでない」と考え、マイクの取得に 失敗したら録音を停止していました。しかしこれは デスクトップ音声は録れているのに録音そのものを捨てる挙動で、 利用者から見ると停止ボタンが消え、一覧に空のアイテムだけが残ります。

結論。相手の発言が残る録音には十分な価値があります。マイクが 取れなくても録音は継続し、自分の発言が入らないことは録音中ずっと出続ける 警告として伝えます。閉じられるエラーとは別枠にしているのは、録音が終わるまで 見えている必要があるためです。

区別していること

  • マイクの失敗 — 録音は続く。警告のみ。
  • 録音自体の失敗 — 何も録れていないので例外。一覧にも残さない。

失敗の理由も言い分ける

当初はマイクの失敗をすべて「権限を許可してください」と案内していました。しかし マイクが 1 つも接続されていない場合、そのアプリは「システム設定 > プライバシーとセキュリティ > マイク」に現れません。存在しないデバイスへの 権限は要求できないためです。この案内は、現れるはずのない項目を探させてしまいます。

getUserMedia のエラー実際の原因案内
NotFoundError 入力デバイスが無い（Mac mini / Mac Studio には内蔵マイクが無い） 外付けマイクの接続を案内する。設定へは誘導しない
NotAllowedError OS またはブラウザに拒否された プライバシー設定へ誘導する
NotReadableError 他アプリが占有している 他のアプリの確認を促す

エラー名はブラウザ実装によって揺れるため、getUserMedia を呼ぶ前に enumerateDevices() で入力デバイスの有無を確かめ、無い場合は 確実に「接続されていない」として扱います。

この方針は React から切り出した関数に置き、「マイク失敗時に停止を呼ばないこと」を テストで固定しています。同じ退行を繰り返さないためです。

ADR-018 レンダラーの CSP

ADR-018

script-src で blob: だけを追加で許可する

発見した不具合

マイクの権限を許可した直後に The user aborted a request. とだけ表示され、マイク入力が録音されない 状態になっていました。権限は通っているのに原因が分からない、最も追いにくい形の失敗です。

原因

マイクの取り込みには AudioWorklet を使い、そのモジュールを Blob URL から 読み込んでいます。当初の CSP は default-src 'self' だけだったため blob: が許可されておらず、addModule() がブロックされていました。 このとき Chromium は理由を示さず、AbortError の既定メッセージだけを返します。

計測結果（Electron で CSP を変えて addModule を試行） default-src 'self' のみ → NG AbortError "The user aborted a request."
script-src に blob: を追加 → OK
CSP ほぼ無制限 → OK
結論。script-src 'self' blob: を追加します。 default-src は 'self' のままに保ち、リモートのスクリプト読み込みは 引き続き許可しません。Blob URL は同一オリジン由来で、レンダラーは外部コンテンツを 読み込まず contextIsolation も有効なため、緩和の範囲は限定的です。

ワークレットを別ファイルにしなかった理由

blob: を使わず実ファイルとして配置する案もありますが、パッケージ済みアプリでは レンダラーが file:// から読み込まれるため、パス解決と 'self' の 扱いが開発時と変わります。Blob なら開発時とパッケージ時で挙動が同じで、 配布物に追加のファイルも要りません。

あわせて直したこと

  • この段階の失敗を MicSetupError として区別し、「マイクの音声処理を 初期化できませんでした」と何に失敗したかを明示するようにした。権限やデバイスの 問題と切り分けられる。
  • CSP の内容をテストで固定した。script-src に blob: と 'self' があること、リモート読み込みを許可しないこと、 media-src に file: があることを検証する。

ADR-019 ウィンドウ外からの録音操作

ADR-019

メニューバーアイコンとアプリケーションメニューの二本立てにする

発見した不具合

ドキュメントには「メニューバーから録音・停止できる」と書いていましたが、 実際には何も表示されていませんでした。原因は 2 つあり、 どちらも単独で表示を妨げます。

原因症状
埋め込んだアイコンの PNG が破損していた ヘッダは正しいが画像データが壊れており、Electron 側では isEmpty: true / サイズ 0x0 の空画像になっていた
Tray の参照を保持していなかった 生成した Tray を変数に入れていなかったため GC で回収され、 仮にアイコンが正しくても消える（Electron でよくある落とし穴）
結論。アイコンは円を描く生成器で作り直し、モジュール参照を 保持するようにしました。あわせてアプリケーションメニューにも「録音」を 追加しています。「メニューバー」は画面右上の常駐アイコンとも、アプリ名の 並ぶメニューとも解釈でき、どちらを探しても見つかる方が確実だからです。 ⌘R で開始、⌘. で停止できます。

  • 録音状態の変化を TransportController から購読できるようにし、 メニューとトレイの表示を追従させる。以前はトレイのクリック時にしか更新しておらず、 ウィンドウ側で停止すると表示が古いままになっていた。

ADR-020 無音区間の文字起こし

ADR-020

whisper の VAD で発話区間だけを渡す

発見した不具合

文字起こしに 「ご視聴ありがとうございました」が頻繁に混ざるという 報告がありました。マイクトラックは会議中ずっと録り続けており、自分が喋るのは 全体の 2 割程度です。残りの無音を whisper に通すと、言語モデルとしての性質から 学習データ（YouTube 字幕）に多い定型句が生成されます。 相手トラックにも同じことが起きます。

手元で再現させた結果がこれです。10 秒の微小ノイズ、発話、20 秒の微小ノイズを 繋いだ音声を渡すと、発話していない 30 秒目に文章が現れました。 

[     0- 12280ms] 来週の予定を確認します

選択肢

方式判定理由
自前のエネルギーベース VAD で前段フィルタ 不採用 追加のモデル配布は不要だが、しきい値の調整が環境依存になる。 発話区間を切り出したあとタイムスタンプを元の時間軸へ戻す処理も自前で持つことになる
whisper へ全体を渡し、無音区間に載ったセグメントを後段で捨てる 不採用 ハルシネーションの発生自体は止められず、無音に対する推論時間も従来どおり掛かる
whisper.cpp の --vad（Silero VAD） 採用 下記
結論。whisper.cpp を v1.7.4 から v1.9.3 へ更新し、 --vad --vad-model で Silero VAD を有効にしました。VAD モデルは 0.9MB と極小なので、モデルカタログに必須として加えています。 同じ音声で試すと、ハルシネーションは消え、発話区間の時刻も 9990-12250ms と正確になりました （VAD 無しでは 0-12280ms と誤っていた）。 タイムスタンプは whisper.cpp が元の音声の時間軸へ戻すため、こちらでの変換は不要です。 （2026-09 訂正）戻されるのは発言の開始・終了だけで、1 つの発言が 複数の発話区間にまたがると間の無音ごと伸びる。ADR-036 で切り直している。

併せて入れた二段構え

  • --suppress-nst で非発話トークンを抑制する。VAD をすり抜けた 雑音の分に効く。
  • 既知の定型句（「ご視聴ありがとうございました」など）を、 セグメント全体が完全一致したときだけ落とす。部分一致で消すと 「資料の共有ありがとうございました」のような本物の発言まで失われるため。

壊さないための逃げ道

  • VAD モデルが未取得・削除済み、または設定で無効にされていれば --vad を渡さない。従来どおり文字起こしは動きます。 ADR-006 の話者分割モデルと同じ扱いです。
  • 設定で古い whisper-cli を指している場合に備え、 --vad を知らないバイナリのエラーは 「v1.7.6 以降に更新するか、設定で無効にしてください」という文言へ翻訳する。

残した判断

マイク取得時の autoGainControl は無音時の室内ノイズを持ち上げるため、 この現象を悪化させている可能性があります。ただし声の小さい話者には有利に働くため、 今回は変更していません。

ADR-021 要約の推論バックエンド（MLX 化）

ADR-021

MLX への移行は見送り、GGUF / node-llama-cpp を継続する

背景

このアプリは macOS 専用（arm64）です。Apple 純正の MLX は Apple Silicon 向けに 最適化されており、2026-03-30 には Ollama が Apple Silicon の推論エンジンを MLX へ 切り替えました。「GGUF ではなく MLX 形式にすれば要約が速くなるのではないか」という 問いが出たため、ADR-004 / ADR-004b を再検討しました。

まず確認した前提

確認したこと結果
既定モデル（Gemma 4 E4B）に MLX 版があるか ある。mlx-community/gemma-4-E4B-it-qat-4bit など、 いま使っている QAT 版に対応する変換が公開されている

つまり「モデルが無いから不要」という理由では却下できません。判断は 速度の実利と移行コストで決めました。

決め手は、このアプリの推論プロファイルが MLX の苦手側にあること

MLX が llama.cpp の 2〜3 倍という数字は、短いプロンプト × 長い生成 （チャット用途の decode）で出たものです。このアプリの要約は逆の形をしています。

観点チャット用途このアプリの要約

MLX は llama.cpp のスライディングウィンドウキャッシュに対して full prefill 戦略を取るため TTFT で不利になりやすく、30K トークンを超える文脈では Flash Attention を 有効にした llama.cpp より約 50% 遅いという計測が報告されています。 defaultSettings() の contextSize: 32_768 は まさにその領域です（ADR-004b）。

ADR-023 モデルの削除とアンインストール時のクリーンアップ（2026-09）

ADR-023

設定画面から 1 件ずつ削除できるようにし、アンインストール時の自動クリーンアップは見送る

背景

ADR-011 でアプリがモデルの入手を引き受けるようにした結果、 ~/Library/Application Support/<app>/models/ には合計 6GB 近くが溜まります。 取得する導線はありましたが、減らす導線がありませんでした。 話者分割（任意）を試してやめた場合や、容量を空けたい場合に手立てがない状態です。

削除するのは「アプリが置いたファイル」だけにする

設定には chooseFile で利用者が自分のファイルを指定する逃げ道があります （外付けドライブに置いた大きなモデルなど）。この参照先を消すと、 アプリが管理していない、他の用途と共有しているかもしれないファイルを 消すことになります。そのため FileModelStore.remove() は models/ 配下だけを対象にし、外部パスに対しては設定の参照を外すに留めます。

一方、models/ 配下のファイルは設定が何を指していても消します。 残すと GetModelStatus が既定の保存場所を見て「取得済み」を返し続け、 削除したのに消えていないように見えるためです。 アーカイブ配布のもの（話者分割）は展開先ディレクトリごと消します — model.onnx だけ消しても同梱の付随ファイルが残り、次の取得で残骸と混ざります。

録音中・処理中は断る

ワーカーが読み込んでいる最中のモデルを消すと、ジョブが途中で失敗します （ADR-008 のワーカー隔離があるのでアプリは落ちませんが、 利用者から見れば原因の分からない失敗です）。DeleteModel は status === 'recording' か isProcessing(steps) の録音があれば断ります。 pending が残るだけの録音（リトライ待ち）は動いていないので妨げません — ADR-010 の「失敗しても他は進む」設計上、 未完了の録音はライブラリに残り続けるためです。

アンインストール時の自動クリーンアップは実現できない

macOS で .app をゴミ箱に入れる削除には、 OS 側のフックが一切ありません。インストーラ形式ではないので アンインストールスクリプトを走らせる仕組みもなく、 サンドボックス化していないため（Core Audio Process Tap の権限のため ADR-014 の署名構成を採っている）コンテナの自動削除も働きません。 つまり「アプリの削除を検知して残りを消す」は設計の選択肢ではなく、不可能です。

代替案判定理由
設定画面に「アプリのデータをすべて削除」ボタン 今回は見送り 唯一確実に動く方法だが、個別削除で容量の問題は解消する。まとめて消す要求が実際に出てから作る
DMG にアンインストーラを同梱 不採用 配布物が増え、署名・公証の対象も増える（ADR-014）。得られるのは残骸の削除だけ
常駐プロセスでアプリの存在を監視 不採用 アプリを消した後も何かが残り続けることになり、目的と矛盾する
結論。個別削除だけを入れます。 残るのは models/・settings.json・work/ で、 いずれも ~/Library/Application Support/ 配下という macOS で残骸が置かれる標準の場所です。 会議の成果物は保存先（ADR-015）にあり、 そちらはアプリを消しても残るべきものなので、そもそもクリーンアップの対象ではありません。

ADR-024 メモリ不足時の重い推論（2026-09）

ADR-024

実行前に空きメモリを確認し、足りなければそのステップだけを失敗させる

背景

要約は 5.15GB のモデルを一度にメモリへ載せます。実機で測ったところ、 モデル本体が約 5.69GB、32K のコンテキストが約 1.27GB で、合計およそ 7GB でした （node-llama-cpp の GgufInsights による見積もり）。

これまでのガードは「ジョブを 1 件ずつ直列に処理する」（ADR-008）と 「要約が終わったら必ず dispose() する」（ADR-004）の 2 つでした。 どちらもアプリ内部の同時実行を防ぐだけで、アプリの外の状況は一切見ていません。 16GB の機体で会議アプリとブラウザが 8GB を使っている状態から要約に入ると、 macOS が圧縮とスワップに追われ、会議そのものを巻き添えにします。

不採用にした案

案見送った理由
足りなければコンテキスト長を下げて実行する（縮退） 分割要約は文脈が切れて決定事項を取りこぼす。ADR-004b で コンテキスト長を選択の決め手にしたのに、それを黙って捨てることになる。 品質が落ちたことは利用者に見えない
空くまで待ってから実行する いつ終わるか分からない処理になる。会議直後に議事録を見たい利用者にとって、 「失敗して再実行できる」方が状況を把握しやすい
ダイアログで利用者に確認する 停止後の処理はバックグラウンドで走る（ADR-009）。 そこに同期的な確認を挟むと、席を外している間ずっと止まる
結論。重いステップに入る前に空きメモリを確認し、足りなければ failStep でそのステップだけを失敗として記録します。 ADR-010 の仕組みにそのまま乗るので、要約が止まっても ミックス・文字起こし・エンコードは完走し、音声と文字起こしは残ります。 利用者は他のアプリを閉じてから、詳細画面の「再実行」を押すだけで済みます。

ガードは二重にする

  • 事前チェック（ProcessRecording）。ネイティブコードに 触れる前に止めるので、失敗が確実に「扱えるエラー」になる。
  • 内蔵ガード（node-llama-cpp）。調べたところ ramPadding は指定しなくても既定で RAM の 25%（上限 6GB）、 vramPadding は VRAM の 8%（上限 1.6GB）を確保していました。 つまり内蔵ガードはすでに効いていたので、こちらの役目は 「保守的」のときに締めることだけです。緩める方向には触りません。 既定を下回る値を渡すと締めるどころか緩めてしまうため、必ず大きい方を採ります。

空きメモリの数え方

os.freemem() は macOS では純粋な free ページしか数えず、常に 「空きが無い」と答えます。そこで vm_stat を読みますが、 どのページを空きとみなすかで答えが 2 倍以上変わります。

数え方同一時点での値
free + inactive + speculative + purgeable4.85GiB（30.3%）
総量 − wired − compressor 占有9.72GiB（60.8%）
kern.memorystatus_level（OS 自身の判断）59%
node-llama-cpp の getVramState().free12.71GB
後者を採ります。前者で実装したところ、実際に要約が動く機体で 「標準」が要約を拒みました（空き 4.91GiB / 必要 8.46GiB）。 動く環境で拒む誤検知は、ガードが無いことより悪い結果です。 active・inactive な匿名ページも、大きな要求が来れば macOS が圧縮して回すため、 空きとして数えてよい。この式は OS が jetsam の判断に使う kern.memorystatus_level と 2 ポイント差で一致しており、 OS 自身の見立てに合わせたことになります。

設定

memoryProtection を「保守的 / 標準 / オフ」の 3 段階で持ちます。既定は「標準」。 「オフ」が外すのは事前チェックだけで、node-llama-cpp の内蔵の余白は そのまま残します。外せば OS が固まりやすくなり、この ADR の目的に反するためです。

見積もりに上乗せする余白は「保守的」が 3GB か総量の 20%（大きい方）で、「標準」は余白を持たず 見積もりそのものが空きに収まるかだけを見ます。「標準」は当初 1GB か 10% の余白を持ち、 次に 0.5GB か 5% へ緩めましたが、16GB 機ではどちらも「オフ」なら問題なく要約できる状況を 拒みました（後者で必要 約 8.2GB / 空き 約 7.6GB。見積もりだけなら 約 7.4GB で収まる）。 見積もりは既に実測より安全側へ丸めてあり、OS を守る余白は node-llama-cpp の内蔵ガード （RAM の 25%）が別に持っているので、「標準」の事前チェックがそれを重ねて持つ必要はありません。

見積もりの精度について

所要メモリはモデルのファイルサイズとコンテキスト長からの粗い見積もりです。 係数は実機の実測（モデルはファイルの約 1.10 倍、KV キャッシュは約 18.4KB/トークン ＋ 固定 0.62GB）に基づき、安全側へ丸めてあります。モデルを差し替えれば係数はずれますが、 桁を外さない見積もりで目的は足ります。テストは実測値を下回らないことと 実測の 1.3 倍を超えないことの両方で固定しており、 過小（素通り）と過大（誤検知）のどちらにも倒れないようにしています。

ADR-025 録りっぱなしの防止（2026-09）

ADR-025

main プロセスで無音を見張り、続いていたら知らせる。自動では停止しない

背景

会議が終わってもアプリを止め忘れると、無音だけの長い録音が残ります。 止め忘れは後段すべてに響き、文字起こしと要約が無音に対して走り、 メモリと時間を無駄に使います。

見張る場所は main

レンダラーには入力レベルのメーター（readInputLevel）が既にありますが、 そこで見張るとウィンドウを閉じている会議中に効きません。 main にはシステム音声（audiotee）もマイク（pushMicPcm）も集まるため、 両トラックの peak をここで見れば、ウィンドウの有無に関係なく判定できます。 DualTrackRecorder には UI 用の systemLevel() とは別に onPeak の購読を足しました。systemLevel() は読み出しで値を 消費する（メーターを落とすため）ので、同じ口を 2 つの消費者で使うと peak を奪い合います。

自動停止はしない

無音が続いていても、会議が静かなだけかもしれません。意図せず録音が切れる損失は、 止め忘れの損失より大きいので、知らせるだけにとどめます。 応答がなければ同じ間隔で繰り返し知らせるので、通知を見逃しても効果は残ります。

知らせ方は OS 通知（「録音を停止」ボタン付き）とアプリ内の確認バーの両方です。 通知はウィンドウを見ていなくても届き、確認バーは通知を見逃して戻ってきたときに気づけます。

判定は domain の純粋な関数に置く

observeLevel（src/domain/SilenceWatch.ts）は時計もタイマーも持たず、 レベルと時刻を受け取って「知らせるべきか」を返すだけです。main 側の createSilenceMonitor が peak を 1 秒の区間にまとめて渡します。

判定は「1 つでも音があれば数え直す」ではなく「区間のうち何割が無音か」で行います。 前者にすると、会議の後で机に戻ってキーボードを打っているだけで計測が延々と 振り出しに戻り、いつまでも知らせられません。1 秒だけの物音では割合がほとんど動かず 計測は続き、会話が始まれば割合が崩れて数え直しになります。 既定は 5 分・しきい値 0.02（peak）・無音の割合 90%（5 分なら 30 秒ぶんの物音まで許容）で、 時間と有効／無効は設定画面から変えられます。

ADR-026 文字起こしの高速化（2026-09）

ADR-026

whisper.cpp の Core ML エンコーダを任意ダウンロードとして採用する。faster-whisper は不採用

背景

「whisper-cli を faster-whisper に置き換えれば速くなり、メモリも減るのではないか」 という問いから始まりました。調べた結果 faster-whisper は不採用ですが、 同じ whisper.cpp のまま使える高速化の手が見つかったので、そちらを採ります。

faster-whisper は Mac では遅くなる

faster-whisper は Python ライブラリで、中身は CTranslate2 です。 よく引かれる「4 倍速い」は OpenAI 純正の PyTorch 実装との比較であって、 whisper.cpp との比較ではありません。

決定的なのは、CTranslate2 に Metal バックエンドが無いことです。 対応 GPU は NVIDIA（CUDA）のみで、Apple Silicon では ARM64 の CPU パスに落ちます。 一方このアプリは scripts/build-whisper.sh で GGML_METAL=ON を立てて GPU 実行しているため、比較は「Metal GPU 対 CPU のみ」になります。

エンコードは 2.0 倍速ですが、デコードは Metal のままなので全体では 1.39 倍です。 メモリは増えません（ADR-024 のメモリガードに影響しない）。 精度も変わらず、句読点を除いた文字列で 99.45% 一致しました — 差は「ごろ↔頃」の表記ゆれと、Core ML 側が Metal の取りこぼした一言を拾った箇所だけです。 セグメント分割はやや細かくなります（105 → 155）。

1.2GB は全員に強いない

エンコーダ（ggml-large-v3-turbo-encoder.mlmodelc）は 1.2GB あり、 モデル本体の 574MB より大きく、初回ダウンロードを 5.7GB から 6.9GB へ押し上げます。 1.4 倍速はそれだけの容量を全員に払わせる差ではないので、 MANAGED_ASSETS に optional: true で足します。 WHISPER_COREML_ALLOW_FALLBACK=ON でビルドしてあるため、 未取得なら従来どおり Metal だけで動きます（実測で確認済み。 stderr にログが 1 行出るだけで終了コードは 0、文字起こし結果も正常）。

初回の +21 秒には手を打ちません。パイプラインは停止後のバックグラウンド処理 （ADR-009）なので、利用者が待たされる場面がないためです。

名前で縛る必要がある

whisper.cpp はエンコーダのパスをモデルのパスから導きます — 拡張子と -q5_0 を落として -encoder.mlmodelc を足す （whisper_get_coreml_path_encoder）。つまり ggml-large-v3-turbo-q5_0.bin の隣に ggml-large-v3-turbo-encoder.mlmodelc という名前でしか置けません。 設定に書く項目は無く、applyTo は空のパッチを返します。 この対応が崩れるとCore ML が黙って無効になる（速度が戻るだけでエラーは出ない）ので、 テストで両者のファイル名を突き合わせています。

配布物が zip なので FileModelStore.extract に分岐を足しました。 unzip ではなく ditto -x -k を使うのは、Apple 製 zip に入っている __MACOSX を models ディレクトリに撒かないためです — unzip だと remove() が消し切れない残骸になります （ADR-023）。

開発時の注意

npm run setup が入れる Homebrew の whisper-cpp は Core ML 無しでビルドされています。手元で高速化を確認するときは npm run build:whisper でビルドしたものを設定でパス指定してください。 build-whisper.sh は既存バイナリの otool -L を見て、 Core ML を含まない古いビルドなら自動で作り直します。

ADR-027 録音の開始忘れの防止（2026-09）

ADR-027

他のアプリのマイク使用を見張り、続いていたら知らせる。自動では開始しない

背景

ADR-025 で止め忘れは防げるようになりましたが、逆向きの 押し忘れ——会議が始まっているのに録音していない——は救えていませんでした。 止め忘れが無駄なファイルを残すだけなのに対し、開始忘れは会議の内容そのものが 失われます。損失が大きいのはこちらです。

信号はマイクの使用状態

「会議が始まっている」ことを表す信号として、他のアプリがマイクを使い続けている ことを見ます。CoreAudio の kAudioDevicePropertyDeviceIsRunningSomewhere を 入力デバイスごとに読むだけで判定でき、次の 3 点で他の案に勝ります。

  • ブラウザの会議も等しく拾える。プロセス名で会議アプリを探す方式だと Zoom や Teams のアプリ版しか分からず、ブラウザの Google Meet を落とします。
  • 追加の権限が要らない。デバイスの状態を読むだけで音声データには触れず、 TCC の許可も録音インジケータの点灯も発生しません。
  • 意味が直接的。「誰かが通話している」ことをそのまま表すので、 アプリが起動しているだけの状態と会議中を取り違えません。

音を常時聴く方式は採らない

ADR-025 の素直な鏡像は「録音していない間も audiotee を回し、 音が続いていたら知らせる」ですが、これは採りません。Core Audio Process Tap を開くことは 実際に録音を始めることで、macOS の録音インジケータが点灯し続けます。 「送らない」を前提にしているアプリが、録音していない間じゅう音を聴いている状態になるのは、 機能の利得に見合いません。音楽や動画でも鳴るため誤検知も増えます。

自動では開始しない

マイクを使っているのが会議とは限りません（音声入力、ボイスメモ、着信の確認）。 意図しない録音が始まる損失は、押し忘れの損失より大きいので、 ADR-025 と対称に知らせるだけにとどめます。知らせ方も同じく OS 通知 （「録音を開始」ボタン付き）とアプリ内の確認バーの両方です。

知らせるのは 1 つの会議につき 1 回

止め忘れは応答があるまで繰り返し知らせますが、こちらは繰り返しません。 「録音しない」と決めた会議の最中に同じ通知が何度も来るのは邪魔でしかない ためです。一度知らせるか「今はしない」を選ばれたら、マイクが空くまで黙り、 会議を抜けて次の会議に入れば再び知らせます。通知を見逃した場合は、 ウィンドウに戻ったときに確認バーが残っています。

判定は domain の純粋な関数に置く

observeMicUsage（src/domain/StartWatch.ts）は ADR-025 の observeLevel と同じ形で、時計もタイマーも 持ちません。判定も同じく区間のうち何割が使用中かで行います。 1 標本でも空きがあれば数え直す方式にすると、会議アプリがデバイスを掴み直すだけで 計測が振り出しに戻るためです。既定は 1 分半・使用の割合 90%・標本間隔 5 秒で、 時間と有効／無効は設定画面から変えられます。

CoreAudio を読むための同梱バイナリ

デバイスの状態は Electron からは読めないため、native/micwatch/main.swift をビルドして同梱します（npm run build:micwatch）。状態が変わったときだけ 1 / 0 を 1 行出す子プロセスで、録音していない間だけ 動かします。録音中は自分自身がマイクを使うので見張っても意味がありません。 同梱物が無い場合（開発中にまだビルドしていない等）は、この機能だけが黙って無効になります。

ADR-028 話者識別の実行方式（2026-09）

ADR-028

WASM 版 sherpa-onnx をやめ、公式プリビルドのネイティブアドオンを使う

背景

40 分を超える録音の話者識別が、何度再試行しても必ず 「memory access out of bounds」や 260476136 のような数値だけのエラーで 失敗していました（35 分なら成功）。マシンの空きメモリとは無関係です。

原因は npm の sherpa-onnx が WASM ビルドであること。 wasm の線形メモリは初期 512MB・上限 2GB で、一度伸びると縮みません。 録音が長くなるほど音声そのものと推論の中間データが積み上がり、上限に達します。 さらにラッパの process() は _malloc の戻り値を検査せず、 確保に失敗しても 0 番地へ音声を書き込んで推論に入るため、 症状がメモリ不足に見えない形で現れます。

計測（同じ音声・同じ v1.13.7・同じ結果）

入力WASMネイティブ
53 秒10.6 秒2.7 秒（1 スレッド）／1.8 秒（2）
46 分相当（合成）683 秒102 秒（4 スレッド）・ピーク RSS 419MB
実際の 46 分の録音何度再試行しても失敗上限そのものが無い
メモリ上限2GB（拡張不可）64bit（実メモリまで）

合成入力（53 秒を繰り返して 46 分にしたもの）では発話の多様性が乏しく、 セグメントが 489 個しか出ずヒープは 512MB のままで、失敗は再現しません。 実録音では話者チャンクがはるかに多く、中間データが上限に届きます。 再現しない条件でも 6.7 倍の速度差は出ており、 どちらの観点でもネイティブが有利です。

選択肢

案判定理由
WASM のまま音声を分割して推論する 不採用 クラスタリングはチャンク内で閉じるため、話者番号がチャンクをまたいで 繋がりません。黙って質が落ちるより失敗させるほうがましで、 そもそも上限を先送りするだけ
CLI バイナリをソースからビルドして同梱（whisper-cli 方式） 見送り クラッシュを完全に隔離できるが、CMake ビルドの追加で package と CI が重くなり、 出力テキストのパースも要る。パイプラインは既に utilityProcess に隔離済み （ADR-008）で、追加の隔離の利得は小さい
公式プリビルドのネイティブアドオン（sherpa-onnx-node） 採用 同じバージョン・同じ結果で上限が消え、4〜6 倍速い。差し替えは DiarizationSessionFactory の seam の中だけで済み、ビルド手順は増えない
WASM を選んでいた理由は無くなった。当初は「ビルド不要で入る」ことを 買っていましたが、sherpa-onnx-node も arm64 の .dylib を プリビルドで配っており、npm install だけで入ります。 node-llama-cpp で既にネイティブアドオンを積んでいるため、扱いも増えません。

設計上の制約

  • asarUnpack は既に node_modules/sherpa-onnx* を対象にしており、 disable-library-validation の entitlement もあるため、 同梱と ad-hoc 署名の設定は変えずに済む。
  • プリビルドは optionalDependencies で OS / CPU ごとに入る。 配布対象は arm64 の macOS だけ（electron-builder.yml）で、CI も arm64 の macos-15 ランナーなので一致する。
  • ネイティブのハンドルに解放 API は無く、GC 時にファイナライザが片付ける。 ワーカーはジョブごとに終了するので（ADR-008）、 そこで確実に OS へ返る。
  • スレッド数は論理コアの半分（上限 4）。全コアを占有すると処理中の操作が重くなり、 4 を超えても速度はほとんど伸びない。

  • 文字起こしは 160 字の窓を半分ずつ重ねて切る。1 チャンク丸ごとでは 業務の話に挟まった 3 発言の雑談が薄まり（0.57）、細かく重ねると 0.65 まで上がった。 重ねないと雑談が窓の境目で割れて落ちる。250 字では結果の抜粋に当たった箇所が映らなかった。

  • 索引作成だけでなく検索でもメモリを確認してからモデルを読む （ADR-024）。会議中に検索されることがあり、そこで黙って 1.9GB を載せると OS ごと重くなる。読み込み済みなら確保済みなので確認しない （空きから引かれた分を要求側にも数えると、動いているモデルを理由に断ってしまう）。
  • 録音中とその後処理の間は同期しない。処理が始まったら同期を止め、ワーカーも終了させて 埋め込みモデルの分のメモリを空ける（要約の ADR-024 のメモリ確認に 引っかからないようにするため）。
  • 意味検索を無効にしたら索引は自動で消す。設定画面に容量と「インデックスを削除」を出す。 保存先を変えると旧保存先の録音分は孤児として消え、戻すと作り直しになる（再生成できるので許容）。

取り込んだ音声には「どの声が誰か」という情報が原理的にありません。 ADR-006 の核は「トラック＝話者を録音時に確定させ、推論を要らなくする」ことで、 1 本のファイルではこれが成立しません。全体を相手側に寄せれば applyDiarization が そのまま効いて 参加者A / 参加者B に分かれ、誤りは「参加者どうしの境目」に留まります。 境目のずれは話者名の付け直しで直せますが、自分と相手の取り違えは直せません。

扱い

  • パイプラインの入力は RecordingSource の判別共用体（dual = 2 トラック録音 / single = 取り込み）。どの WAV をどの話者として起こすかは src/domain/RecordingSource.ts の純粋関数が決め、ProcessRecording に 分岐を持たせない。マイクのパスの有無で見分ける形は採らない —— マイクが取れなかった録音でも mic.wav は空のファイルとして残るため（ADR-017）、 2 つの状況を区別できない。
  • kind を持たない既存の tracks.json は 2 トラックとして読む。 アプリを更新しただけで、処理中だった録音のリトライが壊れないようにするため。 meta.json は変えない。
  • 変換は afconvert -f WAVE -d LEI16@16000 -c 1 --mix。 --mix を付けるのが要点で、-c 1 だけではチャンネルを順序を考えずに 増減するため、片側のマイクに寄って録れた会議では話者が丸ごと消える。 16kHz に揃えるのは話者識別がそのサンプルレートを前提とするため（違うと時刻がずれる）。
  • 対応形式の判定は拡張子のホワイトリストと実際の変換の 2 段構え。 ファイル選択のフィルタとドロップの受け入れは変換より前に答えを出す必要があり、 レンダラーはディスクにも子プロセスにも触れない。一方ホワイトリストは DRM 付きの m4a や 音声トラックの無い mp4 を見抜けないので、実際の変換を最終の権威にする。 断る文面で ffmpeg には触れない（利用者に求めるものではない）。
  • 1 分未満は録音を作る前に断る。境目は tooShortRecording の 1 箇所のまま。録音では停止した時点で録音が既に存在するため全ステップを失敗として記録する しかないが、取り込みは利用者がファイルを選んだ直後なのでその場で理由を返せる。 作ってから畳むと、手で消すしかない行が一覧に残る。
  • 開始日時にはファイルの更新日時を使い、読めなければ現在時刻に落とす。一覧は開始日時順に並び 保存ディレクトリ名もそこから作るので、取り込んだ時刻にすると 3 年前の会議が今日の録音の隣に来る。 タイトルは拡張子を除いたファイル名。取り込み先は未分類で、後からツリーで移動する。
  • 元のファイルは保存先に複製しない。保存先に置くのは変換・エンコードを経た audio.m4a だけで、元のファイルは利用者の管理下にある。
  • 複数ファイルは 1 件ずつ順に変換する（afconvert を並べてもディスクとコアを取り合うだけ）。 1 件の失敗で他を諦めず、ファイル名と理由を集めて返す。後処理は直列のキューに通す —— PipelineClient は抱えている依頼が残っている間ワーカーを終了させないため、 続けて呼ぶと ADR-008 の「1 プロセス 1 ジョブ」が崩れる。

ADR-031 話者名の引き継ぎ（2026-09）

ADR-031

声紋で過去に付けた名前を当て、学習は利用者の名付けだけから行う

背景

話者識別が返すクラスタ名（spk0, spk1…）は 1 つの録音の中でしか 意味を持ちません。同じ相手と毎週会っていても、録音のたびに番号は振り直され、 remote:spk0 が前回と同じ人である保証はありません。結果として、一度 「田中さん」と名付けても次の録音では「参加者A」に戻り、同じ作業を毎回繰り返すことになります。

実測（3D-Speaker CampPlus / sherpa-onnx-node）

声紋の次元192（SpeakerEmbeddingExtractor.dim）
追加で必要なモデル 無し —— 話者分割が使う embeddingModelPath をそのまま読める
同一話者のコサイン類似度概ね 0.65 以上
別話者のコサイン類似度概ね 0.5 未満
compute() が返すベクトルのノルム 8.8〜9.7（正規化されていない。sherpa 本体は SpeakerEmbeddingManager 側で正規化している）

選択肢

論点案判定理由
声紋の取り出し SpeakerEmbeddingExtractor で同じ音をもう一度通す 採用 OfflineSpeakerDiarization はクラスタ番号しか返さず、内部で作った 重心ベクトルを外に出さない。抽出は分割に比べれば軽く、1 人あたり最大 30 秒ぶんで済む
sherpa-onnx の SpeakerEmbeddingManager に照合させる 不採用 照合はコサイン類似度だけで、純粋関数として書けばネイティブ抜きでテストできる。 閾値・2 位との差・名前の重複といったこのアプリ固有の判断を、ネイティブの向こう側に 置く理由が無い
学習の契機 利用者が名前を変えたときだけ登録する 採用 下記
自動で当てた名前もそのまま登録して育てる 不採用 一度の取り違えが声紋に混ざり、次の取り違えを呼ぶ。利用者は誤りに気付かないまま 精度が落ちていき、どこから壊れたのかを追えない
引き当てた名前の優先度 この録音で既に付いている名前を優先する 採用 「田中さん」を「佐藤さん」に直した録音で話者識別をやり直したとき、声紋の一致を 優先すると直した意味が無くなる
常に声紋の一致を優先する 不採用 推定が利用者の判断を押し戻す。訂正できない機能は、訂正できる誤りを訂正できない誤りに変える
声紋帳の置き場所 保存先ルートの voiceprints.json 採用 録音ライブラリと一体のもので、別のマシンへ移せば呼んでいた名前も付いてくる。 意味検索の索引（ADR-029）と違い再生成できないので userData のキャッシュとしては扱わない
録音を削除したら、その録音由来の声紋も消す 不採用 録音を整理するたびに認識精度が落ちる。声紋は本文ではなく「その人をどう呼ぶか」で、 元の録音とは寿命が違う。設定画面から一覧・個別削除・一括削除できる
声紋帳が育つのは、利用者が明示的に名前を付けたときだけです。 自動で当てた名前は学習に戻しません。「田中さん」と入ったのが実は佐藤さんだった場合、 利用者が直せばそのベクトルは佐藤さんとして登録され、田中さんの声紋は触られません。 誤りが自分自身を強化しないので、間違いは 1 回で終わります。

扱い

  • 照合は閾値（既定 0.6、設定で変更可）に加えて2 位との差 0.05 以上を要求する。 似た声が 2 人登録されていて僅差で競っている状況は、どちらを選んでも半々の賭けになる。 当てにいかず「参加者A」のままにすれば、利用者が付け直せる。
  • 1 つの名前が複数の話者に当たったら、最も似ている 1 人にだけ付ける。 同じ会議に同じ人が 2 人いることはない。
  • 声紋に使うのは 1 秒以上のターンだけで、合計 3 秒に満たない話者は声紋を作らない （src/infrastructure/diarization/voiceSamples.ts）。 「はい」「なるほど」といった相槌は声の特徴より前後の無音が支配的で、混ぜるほど 声紋が平均へ寄って誰とも一致しなくなる。上限は 1 人 30 秒 —— それ以上渡しても精度は変わらない。
  • 話者ごとの声紋は録音ディレクトリの voices.json に残す。名前を付けるのは パイプラインが終わった何日も後で、そのときには work/ の WAV が消えている。 Speaker 型に持たせない —— あれは IPC で renderer まで渡る DTO で、 192 個の数値を毎回運ぶ理由が無い。
  • PIPELINE_STEPS は変えない（ADR-030）。 すべて diarize ステップの中で完結する。
  • 声紋の抽出に失敗しても話者識別そのものは通す。名前の自動適用は「付け直す手間を省く」 だけの働きで、これが動かなくても話者の分離という本体は完成している。 利用者から見れば従来どおり「参加者A」が並ぶだけで、手で付け直せる。
  • 声紋には埋め込みモデルのファイル名を添える。モデルを入れ替えたら過去のベクトルとは 比較できないため、一致の判定からも平均からも除く。
  • 声紋は長さ 1 に正規化してから渡す（SpeakerEmbeddingPort の契約）。 SpeakerEmbeddingExtractor.compute() は正規化しない。忘れると内積が 「ノルム × コサイン」になり、閾値 0.6 も 2 位との差 0.05 も桁ごと押し上げられて機能せず、 別人でも必ず登録済みの名前が付く。実装中に実際に踏んだ。
  • 声紋は出所（どの録音のどの話者に付けた名前か）と、その元のベクトルを持つ。 平均した結果だけでは、名前を付け直したときに古い名前から 1 件ぶんを引き算で戻せない。 「田中さん」を「佐藤さん」に直したのに田中さん側が同じベクトルのまま残ると、次の録音で 1 位と 2 位が同点になり「差が無いなら当てにいかない」規則で両方とも弾かれる （＝その人は二度と自動判定されない）。取り消しまでが訂正の一部。 同じ話者に何度名前を付け直しても出所は 1 件のままなので、学習の数も水増しされない。
  • 既に付いている名前が既定の採番（「参加者A」など）と同じなら、引き当てに譲る。 利用者が付けたものではないため。これで、声紋帳が育った後に過去の録音の話者識別を やり直せば名前が入る。
  • NaN を含むベクトルは読み込み口で弾く。内積が NaN になると score < threshold も差の判定も「比較が常に偽」で素通りし、 壊れたファイルが最も確信度の高い候補として振る舞う。
  • 抽出より先に前回の voices.json を捨てる。クラスタ番号は実行のたびに 振り直されるので、抽出に失敗したまま古い声紋が残ると、次に名前を付けたときに 別人のベクトルをその名前で覚える。声紋帳は作り直せない。

ADR-032 チャットの絞り込み（2026-09）

ADR-032

どの録音を見るかは純粋関数で決め、tool calling を使わない

背景

録音ごとの議事録は作れても、「先週の TODO をまとめて」「先週の自分の発言だけを要約して」 のような録音をまたぐ問いに答える手段がありませんでした。意味検索 （ADR-029）は上位数件の抜粋を返すだけで、網羅を求める問いには 足りません。ライブラリ全体を相手にする対話が要ります。

このとき「どの録音を文脈に載せるか」を誰が決めるかが分かれ目になります。一般的な作りでは LLM に関数（期間で絞る・検索する）を呼ばせますが、要約と同じ Gemma 4 E4B は 4B 級で、 日付の計算と JSON の生成をしばしば外します。

選択肢

論点案判定理由
絞り込みの主体 domain の純粋関数が決める 採用 決めた内容（「先週（08/31〜09/06）の 2 件」）を画面に出せるので、外していれば 利用者が言い直せる。判断はモデル抜きで全件テストできる
LLM の tool calling に任せる 不採用 外したことが出力から見えない。それらしい期間の議事録が返るだけで、 利用者は誤りに気付けない。表現の柔軟さと引き換えにできる性質ではない
文脈の素材 既定は要約、話者を絞るときだけ文字起こし 採用 要約は既に構造化されていて密度が高い。ただし誰の発言かを保っていないので、 「自分の発言だけ」には答えられない。5GB のモデルを載せる前に無駄な I/O もしない
常に文字起こし全文を map-reduce する 不採用 録音 5 件でも数分かかる。対話のテンポに乗らない
予算の割り当て 録音のあいだで等分し、余りを再配分する 採用 新しい順に素朴に詰めると、長い 1 件が予算を食い尽くして残りが全部落ちる
入るだけ新しい順に詰める 不採用 同上。しかも落ちたことが答えに現れないので、モデルが「全部を見た」前提で断定する
会話履歴の持ち主 renderer が持ち、毎ターン全部を送る 採用 ワーカーはアイドルでプロセスごと終わる（ADR-033）ので、 そこに置くとメモリを返した瞬間に会話が消える。画面が持てば「新しい会話」も 「再起動で消える」も state そのもので表せ、永続化しないことが既定になる
ワーカーのセッションに持たせる 不採用 寿命が合わない。加えて、毎ターン作り直す文脈が KV に積み上がって 32K がすぐ埋まる
モデルがするのは「渡された文脈を読んで答える」ことだけです。 期間・話者・話題での絞り込みは src/domain/DateExpression.ts と src/domain/ChatQuery.ts の純粋関数が決め、結果は「対象: 先週（08/31〜09/06）の 2 件」 として画面に出ます。答えの根拠は [1] [2] の番号で示され、 引用から元の録音へ飛べます。

扱い

  • 週の始まりは月曜。業務の週が月〜金なので「先週の TODO」は月曜からの 一週間を指す。日曜始まりだと、日曜に振り返ったときの「先週」が今週の前半を含む。
  • 日付はローカル時刻のメソッドだけで計算する（getUTC* を使わない）。 利用者の言う「昨日」は利用者の時計の昨日で、UTC で計算すると深夜や早朝の録音が隣の日に滑る。 保存ディレクトリ名（slugForRecording）と同じ流儀。
  • 日付の言い回しが複数当たったら最も長いものを 1 つだけ採る。 「先週の月曜」のような複合と曜日単独は扱わない —— 当たらなければ期間で絞らないだけだが、 取り違えると別の週の議事録をそれらしく返してしまう。
  • 話者の指定は「〜の発言」「〜が言った」の形でだけ拾う。「私はA社の担当です」のような 文脈で一人称が出ただけで自分の発言に絞ると、相手の発言が丸ごと消えた要約を、 絞ったと気づかないまま読むことになる。
  • 意味検索が使えない構成では話題語での絞り込みをしない。 使えないときの「該当なし」は検索結果ではなく単に確かめられなかっただけで、それで候補を 落とすと期間で答えられる問いまで「記録がありません」になる。実装中に実際に踏んだ。 検索が失敗したときに期間だけで答えるのも同じ理由。
  • 期間で絞った結果が空なら意味検索を呼ばない。利用者が指定した期間の外を勝手に見に行かない。
  • 1 録音あたりの割り当てが 400 字を下回るなら、その録音は載せずに件数だけ数える。 数百字の断片は要約としても引用としても役に立たず、モデルを混乱させる。 落とした件数は文脈の末尾に書く。
  • 文脈が空でもモデルには尋ねる。「記録からは分かりません」と答えるのも回答のうちで、 例外にすると会話が途切れて言い直しにくい。ただし空欄では渡さない —— 「（該当する会議の記録はありません）」と書かないと、モデルが記憶から会議を作り出す。
  • チャットのプロンプトは設定で編集できるようにしない。 要約プロンプト（ADR-012）と違い「文脈だけを根拠にする」 「番号で引用する」という出力の契約を含み、画面の引用表示がそれに依存する。 書き換えられると UI が黙って壊れる。
  • 履歴に載せるのは質問と回答の本文だけで、文脈（要約の本文）は載せない。載せるとターンの たびにコンテキストが二乗で膨らむ。代わりに毎ターン最新の文脈を作り直す。
  • PIPELINE_STEPS は変えない（ADR-030）。 チャットはパイプラインの外にあり、既存の成果物を読むだけ。

ADR-033 3 つのモデルの調停（2026-09）

ADR-033

チャットは専用ワーカーで動かし、パイプラインに譲り索引より優先する

背景

チャットが加わって、同じ機体で取り合うモデルが 3 種類になりました —— 文字起こし（whisper、約 0.6GB）、要約とチャット（Gemma 4 E4B、約 5.2GB）、 意味検索の埋め込み（bge-m3、約 0.6GB）。16GB の機体では同時に載せられません。

選択肢

論点案判定理由
チャットを動かす場所 専用の utilityProcess（アイドル 2 分で終了） 採用 会話が続く間はモデルを温めておける。5.2GB のロードは十数秒かかり、 ターンごとに読み直しては会話にならない。返すのはプロセスの終了で確実に行う （ADR-008）
パイプラインのワーカーを間借りする 不採用 あちらは 1 ジョブごとに kill する設計なので、毎ターン読み直しになる
main プロセスで直接動かす 不採用 llama.cpp のクラッシュが main を巻き込み、録音中ならアプリごと落ちる
埋め込みモデルの置き場所 意味検索のワーカーに置いたまま、main が橋渡しする 採用 チャットのワーカーは parentPort 越しに候補を main へ問い合わせ、 main が SearchClient で解決して返す。解決したらすぐ埋め込みを解放させる
チャットのワーカーに両方載せる 不採用 5.2GB ＋ 0.6GB を 1 プロセスに置くと 16GB の機体で破綻する
優先順位 パイプライン ＞ チャット ＞ 索引の同期 採用 録音とその後処理は取り返しがつかない。チャットは利用者が画面で待っている。 索引は後でいつでも作り直せる
先に来た依頼から順に処理する 不採用 会議の最中に索引の同期が走って、録音の音声が途切れかねない
チャットのワーカーは会話の間だけ生き、パイプラインが動き出せば譲ります。 パイプラインの稼働中に届いた問いは、ワーカーを起こさずに断ります —— 文字起こしと要約に加えて 5.2GB を載せると、会議アプリの音声まで途切れかねません。

扱い

  • アイドルは 2 分（意味検索は 3 分）。抱える量が桁で違うので短く返す。
  • パイプラインが始まっても生成中の回答は打ち切らない。数秒で終わるうえ、 利用者が画面で待っている。片付き次第プロセスを終わらせる。
  • 問いを受けたら先に索引の同期を止め、埋め込みモデルを解放させる。
  • 生成は 1 件ずつ。新しい問いが来たら前の問いを中断する。打ち直したのに前の答えが後から 流れてくると、どちらを読んでいるのか分からなくなる。
  • 中断は例外にせず、途中まで生成した文を返す（stopOnAbortSignal）。 利用者が読みかけていた答えを消さない。
  • モデルのパス・コンテキスト長・メモリ保護が変わったらワーカーを終わらせる。 セッションは起動時の設定でモデルを読んだまま生き続けるので、差し替えはプロセスを 作り直すことでしか反映できない。
  • 重い推論の前に空きメモリを確かめる（ADR-024）。要約と同じモデル・ 同じコンテキスト長なので見積もりの係数もそのまま使う。足りなければモデルを読まずに断る。
  • ChatCompletionPort は SummarizationPort と統合しない。あちらは 分割と統合の業務ルールを抱えた「文字起こし 1 本 → 議事録 1 本」で、要求が重ならない。 既存に onChunk を足すと、使わない ProcessRecording まで引数を運ぶ。

ADR-034 過去の録音からの声紋の取り直し（2026-09）

ADR-034

声紋は audio.m4a から取り直す。話者識別はやり直さず、名前付けの裏で 1 回だけ走らせる

背景

ADR-031 の声紋帳が育つのは RenameSpeaker だけで、そこは 録音ディレクトリの voices.json を読みます。ところが voices.json は diarize ステップでしか書かれず、中間 WAV（userData/work/）は完了時に消えるため、 既に録り終えた録音では作る手段がありませんでした。話者に名前を付けるのはパイプラインが 終わった後、というのが普通の使い方なのに、機能が入る前の録音では名前を付けても 黙って捨てられていた状態です。diarize を個別リトライしても readTracks が空を返して「録音データが見つかりません」で止まります。

併せて、SpeakerEmbeddingExtractor.compute() は既定で外部バッファ （napi_create_external_arraybuffer）に声紋を載せて返しますが、Electron の V8 は サンドボックスが有効で外部バッファを禁じており「External buffers are not allowed」で 必ず失敗していました。素の Node では通るため、単体テストも手元の node での 試行も緑のまま、アプリでだけ声紋が取れません。実機で動かして初めて分かりました。

選択肢

論点案判定理由
取り直しの入力 保存先の audio.m4a を 16kHz モノラルへ戻す 採用 録音と一緒に必ず残っている唯一の音。既に 16kHz モノラルで保存されているので リサンプルもダウンミックスも起きず、変換で失うのは AAC-LC の圧縮ぶんだけ （ADR-005）
system.wav（相手トラック）を消さずに残す 不採用 保存容量が跳ね上がる。1 時間の会議で 115MB の無圧縮 WAV を、使うか分からない 「後で名前を付けるかもしれない」ために全録音ぶん抱えることになる
過去の録音は諦める 不採用 名前を付けるのは後からという使い方では、機能そのものが働かない
話者の割り当て transcript.json に残っているクラスタを使う 採用 推論を増やさずに済む。利用者が画面で見ている話者の並びがそのまま使える
話者識別をやり直す 不採用 クラスタ番号は実行のたびに振り直される。既に付けた名前との対応が崩れ、 名前を付け直そうとした利用者の目の前で話者の並びが変わる
自分の声の扱い self の発話と重なる区間を引く（前後 200ms 広げて） 採用 audio.m4a はミックス済みで、diarize が使う system.wav と違い 自分の相槌が入っている。誰がいつ喋ったかは文字起こしで確定しているので推定は要らない。 ガードは文字起こしの時刻のぶれと AAC のプライミングのぶん
そのまま使う 不採用 相手の声紋に自分の声が混ざる。1 人あたり十数秒あれば足りる （selectVoiceRanges）ので、削りすぎる心配より混ざる害が大きい
走らせる時機 最初の名前付けの裏で、1 録音につき 1 回 採用 名前は即座に反映し、声紋の登録だけが後から追いつく。できた voices.json がそのままキャッシュになるので、同じ録音の 2 人目以降では 変換も抽出も走らない
詳細画面を開いたときに先回りする 不採用 見ただけの録音でも数 GB のネイティブを動かすことになる
圧縮由来の声紋の区別 区別しない 採用 おかしくなれば設定の「覚えた声」から名前ごと消せる。重みを下げる案は、 どれだけ下げるかの根拠が実測なしには出せない

決定

  • ExtractVoices が audio.m4a を afconvert で 16000Hz 固定の WAV に戻し、transcript.json から組み直した ターンで声紋を取り、voices.json に書く。サンプルレートを設定値ではなく 固定にしたのは、設定を変えた後に取り直しても過去の声紋と比べられる値にするため。
  • 一時 WAV（1 時間で約 115MB）は withVoicesWav が貸して必ず捨てる。 保存先ではなく work/ に置く。
  • 声紋帳への登録を RenameSpeaker から RememberSpeakerVoice へ 切り出し、main 側の列で 1 件ずつ直列に流す。voiceprints.json が 読んで書き戻す形なので並行させると片方の登録が消えること、続けて名前を付けたときに 重い処理を 1 回に抑えることの両方が理由。声紋帳が育つのは、この列を呼ぶ リネームの 1 か所だけ（ADR-031）。
  • 覚えられなかったことは詳細画面に 1 行出す。黙って捨てると、利用者から見える手がかりは 「設定の『覚えた声』に何も増えない」だけになり、次の録音で「参加者A」に戻って初めて気付く。
  • クラスタの付いていない裸の remote は対象にしない。話者が分かれていない録音で 複数人を混ぜた 1 本を誰かの声として覚えると、次の録音で取り違える。
  • compute() には enableExternalBuffer = false を渡す。
  • PIPELINE_STEPS は変えない（ADR-030）。これはステップでは なく、必要になったとき 1 回だけ走る取り直し処理。

結果

  • 合成した会議（Apple の音声合成 3 話者・AAC-LC 32kbps）で、2 人ぶんの名前を続けて付けると voices.json が 1 回だけ作られ、voiceprints.json に 2 件並ぶことを 実機で確認した。
  • 圧縮と実際の声での精度は未測定。合成音声は埋め込みが互いに 0.93 前後 （同一話者 0.96）で詰まっており、閾値 0.6 の妥当性を測る材料にならない。本番の録音で system.wav から作った声紋と audio.m4a から取り直したものを 突き合わせて確かめる必要がある。

ADR-035 保存データの形式の変更に備える（2026-09）

ADR-035

アプリのバージョンではなくファイルごとのスキーマ番号を持つ。理解できなかったものは上書きで消さない

背景

いずれ保存データの形を破壊的に変えたくなる（ADR-030 で PIPELINE_STEPS に要素を足せなくなったのはその一例）。そのとき古いデータを正しく 変換するには、各ファイルがどの形で書かれたかが分かっている必要がある。当初は 「アプリのバージョンを保存しておく」案を検討した。

併せて現状を調べると、形式を変えなくてもデータを失う経路があった。

  • voiceprints.json / folders.json は、読めなかったとき空として扱い、 次の書き込みで新しい 1 件だけで上書きする。声紋帳もフォルダ定義も再生成できない （ADR-031）。
  • settings.json は、読めなかったとき既定値で起動し、次の保存で storageDir: null を含む内容で上書きする。利用者からはライブラリが丸ごと消えたように見える。
  • 知らないキーや要素を落として書き戻す。新しい版が項目を足したファイルを古い版で一度保存すると、 足した項目が消える。保存先は利用者が選んだフォルダで、別のマシンへ移すことも想定している （ADR-031）ので、新しい版のデータを古い版が開くことは 実際に起こる。

選択肢

論点案判定理由
形式の識別 ファイルごとの整数のスキーマ番号（schemaVersion） 採用 破壊的に変えたときだけ上がるので、変換は v1→v2→v3 と 1 段ずつ順に適用すればよい。 ファイルごとに別々のタイミングで変えられる
アプリのバージョン（0.1.1） 不採用 形式が変わらないリリースでも上がるので、変換の分岐が semver の範囲比較になる。 1 つの番号で全ファイルを表すことになり、別ブランチの開発ビルドも区別できない。 調査のための付帯情報として残すのはよいが、分岐の条件には使わない
キャッシュの扱い 番号が合わなければ捨てて作り直す 採用 index.json と意味検索の索引（ADR-029）は再生成できる。 索引は既にこの形（FILE_VERSION）
キャッシュも変換する 不採用 作り直せるものに変換のコードとテストを抱える理由がない
読めないファイル 書き込む前に <名前>.unreadable-<時刻> へ退避する 採用 起動は止めず（既存の方針）、元の内容は手で取り戻せる形で残る。読むだけの操作では ファイルに触れない
書き込みを拒む 不採用 設定が保存できなくなると、保存先を選び直すこともできずアプリが使えなくなる
知らないキー・要素 読んだ生の内容に重ねて書き戻す 採用 項目の追加（非破壊的な変更）なら番号を上げずに済み、古い版で保存しても消えない
理解できた部分だけを書く（従来） 不採用 古い版を 1 回使うだけで新しい版のデータが欠ける

決定

  • 理解できなかったものを、理解できた部分だけで上書きしない。読めないファイルは 書き込み前に退避し、知らないキーや要素は書き戻しで残す。
  • データをキャッシュ（index.json、userData/search/）と正本 （meta.json / transcript.json / voices.json / folders.json / voiceprints.json / settings.json）に分ける。 変換するのは正本だけ。*.md は人が読むための出力なので番号を持たない。
  • object の正本（settings.json / meta.json / transcript.json / voices.json）には schemaVersion（整数）を持たせる。番号の無いファイルは v1 とみなすので、既存のデータには手を加えない。数値でない番号は「理解できない」として新しい側に倒す。
  • 配列の正本（voiceprints.json / folders.json）は番号を持たせず、 破壊的に変えるときはファイル名を変える（voiceprints.v2.json など）。 { schemaVersion, entries } に包み直すこと自体が破壊的な変更で、0.1.1 はそれを読めずに 空として上書きする。名前を変えれば古い版は古いファイルだけを見るので、ガードが要らない。
  • 自分が知っている番号より新しいファイルは上書きしない（読み取りだけにしてアプリの 更新を促す）。このガードは最初の破壊的な変更より前のリリースに入っていないと 働かないので、変換の仕組みより先に入れる。
  • 番号を上げるのは、名前の変更・単位の変更・構造の組み替えのように意味が変わるときだけ。 項目の追加は既定値で補う読み込み（mergeSettings など）で吸収する。
  • 変換は (vN) => vN+1 の純粋関数を順につなぎ、過去の形の実物をテストの入力に残す。 一度出した変換は書き換えない。録音ごとのファイルは読むときに変換し、書き戻しは次の保存に任せる （起動時の一括変換は、途中で失敗すると新旧が混ざる）。ライブラリ全体のファイルは書き戻す前に 元の内容を残す。

進め方

  1. settings.json / voiceprints.json / folders.json の 退避と、知らないキー・要素の保持。
  2. object の正本への schemaVersion の書き込みと、新しい番号のファイルを上書きしない ガード。meta.json で知らないキーを残すのもここで行う。transcript.json と voices.json はパイプラインが丸ごと作り直すファイルなので、上位の知らないキーは残さない （残すと作り直した中身と食い違う）。文字起こしの手直しでは、読んだセグメントをそのまま持ち回るので セグメント内の知らないキーは残る。
  3. 変換関数をつなぐ仕組みは、最初の破壊的な変更が来たときに作る。

結果

  • 退避したファイルができたことは今のところ利用者に知らせていない（ログに場所を出すだけ）。 実際に起きるようなら画面で知らせる。

ADR-036 VAD の区間をまたぐ発言（2026-09）

ADR-036

whisper-cli のログから VAD の区間の対応表を読み、区間の境目に近い句読点で発言を切り直す

発見した不具合

詳細画面の話者の帯（#65）で、「自分」の帯が話していない間もずっと続いて見えるという 報告があった。マイクはハードウェアでミュートしており、部屋の音を拾うことはない。 その録音の transcript.json では、自分の発言 9 件のうち最長が 642 秒で 22 文字、次が 604 秒で 33 文字だった。

発話 → 60 秒の完全な無音 → 発話 → 60 秒の無音 → 発話、という音声を同梱の whisper-cli （1.9.3）に --vad 付きで通すと、3 つの発話が 0-124980ms の 1 つの発言にまとまった。whisper.cpp は VAD で無音を詰めた音声を文字起こしし、 発言の開始・終了だけを元の時間軸へ戻す。詰めた音声の上では 3 つの発話が 0.2 秒の間隔で並ぶので、whisper は 1 つの文として扱い、戻した区間は間の無音を丸ごと含む。 ADR-020 の「こちらでの変換は不要」はこの場合に成り立たない。

選択肢

方式判定理由
トークンの時刻で間の空いた所を切る 不採用 --output-json-full のトークンの時刻は、詰めたあとの時間軸のまま戻されない。 元の時間軸で間が空いているかを、トークンだけでは判断できない
--max-len 1 で 1 トークンずつ発言にする 不採用 時刻は戻されるが、無音が隣のトークンに吸われる（実測で「了」が 26.2〜62.5 秒）。 境目が正確に取れないうえ、文としての区切りを自前で組み直すことになる
自前で無音を判定して発言を切る 不採用 ADR-020 で退けた理由（しきい値が環境依存）がそのまま当てはまる。 whisper が使ったのと同じ区間で切らないと、文字と区間が食い違う
whisper-cli のログから区間の対応表を読む 採用 下記

結論

whisper-cli は VAD を使うと、区間ごとに元の時刻と詰めたあとの時刻の対応 （vad_segment_info: orig_start … vad_end …）をログに出す。VAD を使うときは --no-prints を外してこれを読み、区間の境目ごとに、近くのトークン （詰めたあとの時間軸）の切れ目で発言を切り分ける。切った発言には区間の元の時刻を付け、 whisper の開始・終了の外へは出さない。確信度による除外は切ったあとの発言ごとに行うので、 無音側の空耳だけを落とせる。上の音声では 0-1980 / 62500-63330 / 123390-124980 の 3 つになった。

トークンの時刻のずれ（2026-09 改訂）

当初はトークンを 1 つずつ、時刻を含む区間（無ければ最も近い区間）へ振り分けていた。 say の日本語音声を雑音の無音で挟んだ合成音声（whisper-cli 1.9.4、 large-v3-turbo q5_0）で確かめると、トークンの時刻は区間の境目から最大 0.5 秒ほど ずれる。区間どうしの隙間は詰めたあとで 0.1〜0.2 秒しかないので、振り分けは境目で簡単に外れ、 「わかりました。他」「に何かありますか?特」「ロ|グイン」「インデ|ックス」のような 語の途中での切断や、「、」「。」だけの発言が出た。

そこで、切る場所を句読点に寄せる。区間の境目ごとに、境目から 1 秒以内にある 文末の句読点の直後のうち最も近い所で切る。句読点の直前では切らない （句読点が次の発言の頭に回る、句読点だけの発言になる）。近くに文末が無いときは:

  • 元の時間軸で 3 秒以上空いた境目は、読点の直後、それも無ければ境目に最も近いトークンの 切れ目で切る。残すと無音ごと何分にも伸びる元の不具合に戻るため。句読点の無い発話が 長い無音を挟んで続くときは語の途中で割れうるが、時刻の正しさを優先した。
  • 短い境目は切らず、2 つの区間を 1 つの発言にまとめる。短い間で割れた区間は文の途中の 息継ぎを VAD が割ったもの（「インデ|ックス」の間が 0.23 秒、「検索は、|インデックスの…」が 0.22 秒）が多く、まとめても発言が数秒伸びるだけで済む。

どの区間にまたがるかは、トークンではなく whisper の発言の開始・終了（元の時間軸に戻っている） から決める。上の合成音声（11 の発話が 1 つの発言にまとまったもの）は、発話ごとの 11 件に戻った。

発言の端のずれ（2026-09 再改訂）

ReazonSpeech / FLEURS のクリップを 4〜40 秒の雑音の間で並べた長尺音声で、語の途中で切られた断片が 数十秒離れた発言に付いた（「病」が 25 秒前の発言の末尾に、「しました。」が 36 秒後ろに、 「これ|でいき|ましょう。」が 3 つに）。トークンだけでなく whisper の発言の開始・終了も 区間の境目からずれ、隣の区間に 10〜140ms だけ掛かっていた。その境目は長い無音なので、句読点が無くても 境目に最も近いトークンの切れ目で切られ、区間の外側の 1〜2 トークンが隣の区間へ振られていた （例: 「ジャ@51790-51850」「ン@51890-52000」に対し、区間の境目が 51900 で「ジャ|ン」が選ばれた）。

そこで、発言の頭（お尻）が掛かる長さが 0.3 秒に満たない端の区間は、またいでいない ものとして外す。境目そのものが無くなるので、語の途中での切断が起きない。本物の発話が 0.3 秒に満たない まま区間の端に残るのは相槌 1 つ程度で、外しても文字は隣の発言に残る。区間の内側の長い境目で、 句読点の無いまま切る扱いは変えていない。

区間をまたいでいた発言は、切る所が無くても両端を区間に収める。端の区間を外すと、 残るのが短い間で割れた区間だけになり切らずに終わることがある。そのとき whisper の時刻のまま返すと、 開始・終了が区間の外の無音にあり（詰めたあとの時刻が区間の頭の直前に来ると無音の中へ戻される）、 前後の無音ごと数十秒に伸びた。同じ音声で、発言 20 件がすべて正解の発話の位置に収まり、 1 分前後に伸びていた 5 件も縮んだ。

壊さないための逃げ道

  • ログの形式は whisper.cpp の約束事ではない。対応表が 1 行も読めなければ切り直しをせず、 今までどおりの発言を返す（帯が伸びるだけで、文字は失わない）。
  • トークンの文字を繋いで本文に戻らないとき（マルチバイト文字がトークンの境目で割れた等）と、 時刻を持たないトークンがあるときも切らない。文字の欠けた発言を作らないため。
  • ログを止めないので stderr が増える（発話区間 1 つにつき 3 行）。execFile の 既定の上限 1MB を越えると whisper-cli ごと止められるため、上限を 64MB に上げた。 増えるのはモデルの読み込みと VAD の行で、本文は含まない（本文は --no-prints の有無にかかわらず stdout に出る）。溜めて読むだけで、どこにも保存しない。

残した判断

既に文字起こしを終えた録音は直さない。文字起こしをやり直すと話者識別も走り直し、 クラスタ番号が振り直されて付けた名前との対応が崩れる（ADR-034 と同じ理由）。 直るのはこの版以降に処理した録音から。

ADR-037 文字起こしの文脈の引き継ぎ（2026-09）

ADR-037

VAD を使わず用語集も空のときだけ --max-context 0 を付け、直前の出力を次のウィンドウへ引き継がせない

背景

whisper は 30 秒のウィンドウごとに文字起こしし、直前の出力をプロンプトとして次のウィンドウへ渡す。 文脈がつながる利点がある一方、一度起きた繰り返しやハルシネーションも次のウィンドウへ持ち越される。 OpenAI の実装でいう condition_on_previous_text=False に当たる設定は、 ハルシネーション対策として広く使われている。

whisper.cpp での扱い（v1.9.4 のソースで確認）

  • プロンプトは、用語集（prompt_past0）と直前の出力（prompt_past1）を 同じ条件 n_max_text_ctx > 0 の中で組み立てる。 --max-context 0 にすると用語集も入らなくなる。
  • --carry-initial-prompt のときは、prompt_past1 がウィンドウごとに空にされ、 直前 1 ウィンドウの出力だけが積まれる。付けないときは最大 223 トークンまで溜まる。
  • --max-context を小さな値にすると、用語集は先頭から切られる。 安全な値を決めるには用語集のトークン数が要るが、アプリ側にトークナイザは無い。
  • 温度フォールバックで温度が 0.5 以上になったときと、音声の終わりに短い残りがあるときは、 whisper.cpp がもともと履歴を捨てている。

合成音声での比較

say の日本語読み上げに雑音を混ぜた 4〜5 分の音声 3 本（発言の間に雑音だけの長い間がある会議、 相づちの連続、声の重なりと小声）を、同梱の whisper-cli 1.9.4 と turbo q5_0 に アプリと同じ引数で通した。

構成引き継ぐ（既定）--max-context 0
VAD 無し 3 本中 2 本で、途中から録音の最後まで同じ文を繰り返し（84 回など）、 後ろの本物の発言がすべて消えた。残る 1 本も実在しない相づちが約 10 件 ループは起きない。無音区間の定型句は出るが既存のブロックリストで落ちる。小声の区間で作り話が 1 件
VAD 有り（既定） 3 本ともハルシネーション無し 得るものが無く、後半の句読点が消え、重なった小さな声（本物の発話）を 2 件取りこぼした

ループしたセグメントの平均対数確率は -0.03 前後と高く、確信度による除外（-1.0）では落とせない。

選択肢

方式判定理由
常に --max-context 0 不採用 用語集が黙って効かなくなる。VAD 有りでは精度が下がるだけ
用語集が空なら --max-context 0 不採用 既定の VAD 有りの構成で、句読点と小さな声を失うだけになる（上の比較）
用語集があるときは小さな --max-context にする 不採用 用語集のトークン数が分からず、値が足りないと用語集の先頭が黙って切られる
VAD を使わず用語集も空のときだけ --max-context 0 採用 ループで発言が丸ごと消える被害が出るのは VAD 無しのときで、そこだけ止める。 VAD モデルが未取得・削除済み、または設定で無効にしたときがこれに当たる （ADR-020 の逃げ道）

残した判断

  • VAD 有りでも実際の会議では繰り返しが起きうる（ADR-022 の比較で観測されている）。 合成音声では再現できなかったので、ここでは扱わず、出力側で繰り返しを検出して落とす仕組みで拾う。 用語集があるときの繰り返しも同じ扱い。
  • 比較は合成音声で、実際の会議より綺麗。実録音で差が出たら見直す。

用語集がそのまま出力される現象への対処は見送る（2026-09 追記）

--carry-initial-prompt で用語集をウィンドウごとに付けているので、無音や雑音の区間で whisper が用語集そのものを書き出す（プロンプトの再出力）懸念があった。本文が用語の列挙だけでできた セグメントを落とす関門を検討し、先に現象が起きるかを npm run eval:transcription の 合成音声で確かめた。

  • 台本に出てこない語だけで用語集を作り、出力に 1 語でも現れたら再出力とみなした。 短い用語集（10 語）と、上限の 200 文字を超える長い用語集（英語の製品名・人名・カタカナ語）の両方で、 5 本 × VAD の有無の 10 通りを起こした。
  • 用語集の語が現れたセグメントは、既存の関門を通す前も後も0 件だった。 落とす対象が無いので、関門は足さない。
  • 用語集があって VAD 無しの構成では、無音区間に直前の発言の繰り返しが出て、ループに呑まれた発話の 取りこぼしが増えた（meeting で 10 件中 5 件。用語集が無ければ 0 件）。用語集があると --max-context 0 を付けないためで、用語集の再出力ではない。VAD 有り（既定）では 用語集の有無で大きな差は無かった（CER の差は 0.03 以内）。

実際の録音で用語集の語が無音区間に出ることが分かったら、この判断を見直す。

ADR-038 繰り返しのループの除去（2026-09）

ADR-038

セグメント内で 8 回以上続く語句を 1 回に縮め、間を空けずに 4 回以上続く同じ文は最初の 1 つだけ残す

背景

ADR-037 の比較で、whisper が同じ文を録音の最後まで繰り返すループを再現した （84 回、60 回）。ループしたセグメントの平均対数確率は -0.03 前後と高く、確信度による除外（-1.0）では 落とせない。ADR-022 で触れた「1 発話で同じ語句を繰り返す」現象も同じ性質を持つ。 --max-context 0 で防げるのは VAD を使わない構成だけで、VAD 有りや用語集があるときの ループは出力側で取り除くしかない。

2 つの形

形扱い理由
セグメント内で同じ語句（30 文字まで）が 8 回以上続く 1 回に縮める ループの前に本物の発言が載っていることがある（実測で「木曜の午前中に共有します」の後ろに 相づちのループ）。セグメントごと落とすとそれを失う。数字だけの単位（「100000000」の 0）は縮めない
前の終わりから 1 秒以内に始まる同じ文が 4 つ以上続く（句読点と空白の揺れは無視） 最初の 1 つだけ残す 最初の 1 つはループの種になった本物の発言であることがある。作り話でも 1 行で済む。 間の条件は、マイクのトラックで間を置いた「はい。」が並ぶのを巻き込まないため （相手の声は別トラックなので、自分の相づちだけが並ぶのは普通のこと）

縮めてから定型句や確信度の関門に掛ける（繰り返された「ご視聴ありがとうございました」も定型句として落ちる）。 セグメントをまたぐ判定は、他の関門を通ったものだけで行う。 落とした分は計測モード（OMR_LOG_DROPPED_SEGMENTS）で理由 repetition として出す。 セグメント内で縮めたときは、削った部分の文字を出す。

合成音声での確認

ADR-037 の 12 通りの出力に通した。VAD 無しで起きた 2 つのループは、 84 行が 3 行、60 行あまりが 1 行になった。実在しない「はい」11 回の連呼は「はい、はい。」に縮んだ。 VAD 有りの 6 通りでは 1 件も手を加えなかった（人が読んだ 3 回の相づちの繰り返しも残る）。

選択肢

方式判定理由
gzip の圧縮率で判定する（OpenAI の実装の compression_ratio_threshold） 不採用 セグメントごとの指標で、短いセグメントが何十も続くループは捉えられない。 どこを削るかも決まらず、セグメントごと落とすことになる
whisper にやり直させる（--entropy-thold を下げる） 不採用 既定の 2.4 でループが素通りしている。上げ下げの効果が読めず、やり直しの分だけ遅くなる
繰り返しの形で取り除く 採用 上記

残した判断

  • ループが呑み込んだ本物の発言は戻らない（VAD 無しの比較では、ループの後ろの発言がすべて失われていた）。 取り除けるのは作り話だけで、ループを起こさせないのは ADR-037 の役目。
  • 「はい、はい、はい。」と「はい、はい、そうですね、はい。」のように少しずつ違う文が交互に続く形は、 同じ文の連続ではないので残る。実例は合成音声で約 10 行だった。
  • 閾値（8 回・4 回・1 秒）は合成音声で決めた。実録音の計測モードで見直す。

ADR-039 モデルの版の固定と更新（2026-09）

ADR-039

取得先をコミットで固定し、手元のファイルは上流ではなくアプリのカタログと比べて「更新あり」を出す

背景

モデルの一覧に「ダウンロード済みのモデルに更新があれば知らせる」仕組みを検討した。調べると、 問題は上流の更新を見逃すことではなく、次の 2 つだった。

  • Hugging Face の URL が resolve/main を指していた。カタログは sha256 を固定しているので、 上流がファイルを差し替えると新しく入れる利用者のダウンロードがチェックサムの不一致で必ず失敗する。
  • 「取得済み」はファイルの有無だけで決めていた。アプリの更新でカタログのモデルを差し替えても、 保存名が同じなら古いファイルが黙って使われ続け、保存名が変われば設定が古いファイルを指したまま残る。

決定

  • Hugging Face の URL はコミットで固定する。GitHub のリリース資産も差し替えうるので、全ファイルに sha256 を持たせる（テストで強制）。
  • 取得したときに、配布物の sha256 を models/installed.json に記録する。 一覧では記録とカタログを比べ、違えば「更新あり」と更新ボタンを出す。
  • 更新は録音中・処理中は断る（削除と同じ）。別名で受け取ってから差し替えるので、失敗しても古いファイルで動き続ける。 保存名が変わった版なら、前の版のファイルを消す。

選択肢

方式判定理由
上流（Hugging Face）の最新と比べて知らせる 不採用 上流の差し替えをそのまま採ると、評価を経ていないモデルで文字起こしや要約の質が変わる。 採るなら eval:transcription で前後を比べてからカタログを書き換えるべきで、 それはアプリの更新として届く。一覧を開くたびに外へ問い合わせる必要もなくなる
一覧を開くたびにファイルをハッシュする 不採用 要約モデルだけで 5GB ある。記録（サイズと更新時刻が変わっていなければ信じる）で済ませる
取得時に記録し、カタログと比べる 採用 上記

残した判断

  • この仕組みより前に取得したファイルは、一覧を初めて開いたときに中身をハッシュして記録する（初回だけ数秒）。 チャットの可否の判定など、取得済みかだけを知りたい呼び出しでは更新を確かめず、この待ちを負わせない。
  • アーカイブ由来のもの（Core ML エンコーダ・話者分割モデル）は展開後にアーカイブを消しているため、 記録が無ければ確かめようがなく「更新なし」として扱う。記録はこの版以降の取得から付く。
  • 利用者が自分で選んだ models ディレクトリの外のファイルは比べない。
  • installed.json はファイルから求め直せるキャッシュ。新しい版が書いたものは上書きせず、記録を諦めるだけにする （ADR-035）。

ADR-040 カレンダー連携（2026-09）

ADR-040

EventKit を同梱の Swift ヘルパーで読み、録音タイトルの初期値と話者名の候補にだけ使う

背景

録音のタイトルは「2026-09-27 10:00 の会議」で始まり、話者は「参加者A」で始まる。どちらも後から 手で直していた。録音の開始時刻に重なる予定があれば、そのタイトルと参加者名でこの手間を減らせる。 参加者名は、声紋による話者名の自動適用（ADR-031）の外側を補う候補にもなる。

決定

  • macOS のカレンダーは native/calendarevents/main.swift をビルドして同梱し、子プロセスとして呼ぶ （status / request / events <fromMs> <toMs>）。 置き方と「無ければ機能だけが黙って無効になる」扱いは micwatch（ADR-027）と同じ。 TCC は子プロセスの問い合わせを親のアプリに帰属させるので、許可のダイアログにはアプリの名前と NSCalendarsFullAccessUsageDescription が出る。
  • 設定の「予定からタイトルと参加者を埋める」は既定で切。カレンダーの許可を求めることになるので、 利用者が選んだときだけ使う。入れた時点でまだ聞かれていなければ、その場で許可を求める。
  • 録音開始時に「開始時刻〜5 分後」に重なる予定を引き、pickEventForRecording （src/domain/CalendarEvent.ts）が 1 件選ぶ。終日の予定と自分が辞退した予定は除き、 開始時刻が録音開始に最も近いものを採る。予定の 5 分前までに始めた録音もその予定とみなす。
  • 予定のタイトルは、タイトルの指定が無いときだけ初期値にする。参加者名（自分・会議室や設備・辞退した人を除く）は meta.json の participants に残し、話者名を書き換えるときの候補（datalist）に出す。 候補はこの録音の参加者を先に、声紋帳の名前を後に並べる。
  • 問い合わせはキャプチャの開始と並べて走らせ、応答を待ってから録り始めることはしない。応答は 3 秒で打ち切り、 失敗はすべて「予定なし」として従来の既定タイトルに戻る。

選択肢

方式判定理由
Node のネイティブアドオンで EventKit を呼ぶ 不採用 Electron の版に合わせたビルドが要り、落ちれば main プロセスごと巻き込む。呼ぶのは録音開始時の 1 回だけなので、 子プロセスの起動の重さは問題にならない
Google / Microsoft のカレンダー API を直接読む 不採用 OAuth と外部への通信が要り、完全ローカル（ADR-003）を崩す。 macOS のカレンダーにアカウントを追加すれば、同じ予定を EventKit から読める
参加者名を話者に自動で割り当てる 不採用 予定の参加者と話者クラスタを結び付ける手がかりが無い。当て推量の名前は利用者の訂正より弱く扱うべきで （ADR-031）、候補として出すのが限度
予定を録音の自動開始に使う このADRでは扱わない ADR-025 / ADR-027 の「勝手に始めない」を変える判断で、 メタデータを埋める話とは論点が違う。ADR-041 で扱う

残した判断

  • 参加者名は録音ごとに meta.json に写す。後で予定が変わっても録音時点の顔ぶれが残り、 カレンダーの許可を後から外しても候補は消えない。項目の追加なので形式の番号は上げない（ADR-035）。
  • 名前が同期されない社外の参加者は、メールアドレスの @ より前を候補にする。
  • 取り込んだ音声（ADR-030）には使わない。取り込みの時刻は会議の時刻ではない。

ADR-041 会議の予定を加味した開始忘れの防止（2026-09）

ADR-041

会議 URL 付きの予定の時間帯は早めに促し、利用者が選んだときだけ自動で録音を始める

背景

ADR-027 はマイクの使用だけを信号にしたため、知らせるまで 1 分半待ち、自動では始めなかった。 マイクを使っているのが会議とは限らない（音声入力、ボイスメモ、着信の確認）からだ。 ADR-040 でカレンダーを読めるようになり、「オンライン会議の URL を含む予定の時間帯に マイクが使われている」という、会議をほぼ直接表す信号が手に入った。前提が変わったので判断を見直す。

決定

設定の組み合わせで 3 段階にする。判定は planStartWatch（src/domain/MeetingStart.ts）が持つ。

カレンダー連携自動開始振る舞い
切 （選べない） 従来どおり（ADR-027）。マイクの使用が設定の時間（既定 1 分半）続いたら知らせる
入 切（既定） 会議の予定の時間帯なら 30 秒で知らせ、通知と確認バーに予定の名前を出す。予定が無ければ従来どおり
入 入 会議の予定の時間帯にマイクが 30 秒使われたら録音を始め、「停止して破棄」付きで知らせる。予定が無ければ従来どおり知らせるだけ
  • 「会議の予定」は、URL・場所・本文のどこかに Google Meet / Zoom / Teams の URL を含み、終日でなく、 自分が辞退していない予定。Outlook の safelinks に包まれた URL も中身を見る。ホスト名で判定し、 パスに zoom.us を含むだけの URL は会議とみなさない。
  • 自動開始は会議の予定があるときだけ。予定が無いときにこの設定が効くと、ADR-027 が避けた 「会議ではないマイク使用で録音が始まる」ことが起きる。
  • 自動で始めたら、OS 通知とアプリ内のバーの両方で知らせ、「停止して破棄」を出す。破棄はパイプラインにかけず、 ファイルも一覧の記録も残さない（DiscardRecording）。停止してから削除する 2 手に分けると、その間に パイプラインが走り出し、処理側の書き戻しで消したはずの録音が一覧に戻りうる。
  • 同じ会議では二度自動で始めない。自動で始めた会議と、録音を止めた・破棄した時点の会議は「扱い終えた」として覚え、 以後は会議とみなさない（アプリを再起動すると忘れる）。途中で止めたのは「この会議はもう録らない」という判断で、 推定で押し戻さない。
  • 会議の予定が新たに現れたら、会議前のマイク使用で一度知らせて黙っていても判定し直す （reopenStartWatch）。早めに入室して音声を確かめている間に知らせ済みになり、会議が始まっても 何も起きない、を避ける。予定が終わったときは解かない（延長した会議の最中に再び促さない）。
  • 予定は、マイクが使われている間だけ 1 分おきに「いま〜5 分後」の範囲を引く（meetingLookup）。 5 秒ごとの見張りのたびに calendarevents を起こさない。
  • 見張りは「促す」が切でも、カレンダー連携と自動開始が入っていれば動かす。その場合、予定の無いマイク使用では何もしない。

選択肢

方式判定理由
カレンダー連携を入れたら自動開始する（別の設定を持たない） 不採用 タイトルを埋めたくて連携を入れた人が、アプリの更新後に黙って自動で録音されるようになる。 録ってよいかを確かめる場面が消えるのは、利用者が自分で選んだときだけにする
予定の時刻に合わせて、マイクを待たずに始める 不採用 予定があっても会議に出るとは限らない（別件で欠席、会議が流れた）。実際に通話が始まったことはマイクの使用でしか分からない
自動で止める 不採用 ADR-025 のとおり、無音は会議が静かなだけかもしれない。自動で始めた録音も、止め忘れは無音の見張りが知らせる

残した判断

  • 予定の時間帯に、会議とは別の通話（huddle、電話）をしていても自動で始まる。予定とマイクの使用だけでは見分けられない。 起きたら「停止して破棄」で消せ、同じ予定では二度と始めないので、実害は一度の取り消しで止まる。
  • 開始は手動と同じく renderer を経由する（マイクは renderer でしか取れない）。ウィンドウを閉じていれば開いて前に出る。 隠れている・最小化しているときは表に出さずに始めるが、そのとき AudioWorklet がマイクの音を途切れず送るかは実機で確かめる必要がある。
  • 判定時間の 30 秒は、設定の下限と揃えた固定値。設定の時間の方が短ければそちらを使う。

ADR-042 録音中のメモと印（2026-09）

ADR-042

メモは行ごとの時刻を note.md に埋め、印は bookmarks.json に持ち、どちらも要約の入力に含める

背景

note.md は録音後の自由記述で、録音中には書けなかった。利用者が会議中に気にした論点を残せれば、 後から該当箇所へ戻れるうえ、4B のモデルが落としがちな論点を要約に拾わせる手がかりになる（Issue #37）。 録音中に増やすのは記録だけで、推論はしない（ADR-009 に抵触しない）。

決定

  • 今録っている録音を開くと、詳細画面の代わりに録音中の画面（RecordingLiveView）を出す。 左に経過時間・2 トラックのメーター・「今の発言に印をつける」、右に会議中のメモ。 止めた瞬間に通常の詳細へ戻す（判定は録音の状態ではなく transport を見る showsLiveView）。
  • 録音を始めたら、どの画面にいてもその録音を選んで録音中の画面を開く（recordingToOpen）。 開くのは始めた瞬間だけで、録音中に利用者が別の録音を開き直したときは奪わない。初期設定の途中では動かさない。
  • メモは note.md そのもの。行ごとに書き始めた時点の経過時間を覚え、 - [00:14:32] 本文 の形で埋めて保存する（src/domain/MeetingNotes.ts）。 入力欄には時刻を出さない。録音後のメモ欄では時刻つきの行が一覧になり、押すとその時点の発言へ移動して再生する。
  • 印は bookmarks.json（{schemaVersion, bookmarks: [{atMs}]}）に持つ。再生成できない正本なので、 知らないキーはファイルにも要素にも残す（ADR-035）。キーは ⌘⇧H で、アプリ内だけで効く。
  • 要約プロンプトに {{notes}} を足す。中身はメモの全文と、印を押した時点（15 秒前まで）の発言。 {{notes}} は必須にせず、無いプロンプトでは末尾に付ける。メモは統合の段にだけ渡し、部分要約には混ぜない。
  • 経過時間は画面が Date.now() - startedAtMs で数える。startedAtMs はキャプチャが動き出した後に決まるので、 音声上の時刻よりわずかに小さい値になる。指す発言は検索と同じく「その時刻以前の最後の発言」に寄せるので、ずれは吸収される。

選択肢

方式判定理由
時刻を note.md に埋める 採用 ファイルが 1 つで済み、録音後にメモを書き換えても行と時刻が離れない。人が読んでもそのまま分かる
時刻を別ファイルに行と対応づけて持つ 不採用 録音後に行を足す・消すと対応が崩れる。崩れても利用者からは見えない
メモを 1 件ずつ Enter で積む（チャット風） 不採用 会議中の走り書きは箇条書きの文書に近い。note.md との二重管理にもなる
印をメモの行として埋める 不採用 書いている最中の入力欄に行が差し込まれ、カーソルがずれる
印のキーをグローバルショートカットにする 見送り 利用者の選択でアプリ内に留めた。会議アプリを前面にしたまま押したい要求が出たら、RECORDING_SHORTCUT と同じ形で足す
印の時刻だけを要約に渡し、文字起こしとの突き合わせをモデルに任せる 不採用 4B のモデルは時刻の突き合わせをしばしば外し、外したことが出力から見えない（ADR-032 と同じ理由）

残した判断

  • 印は取り消せない。押し間違えは要約で 1 か所が優先されるだけなので、取り消しは要求が出てから足す。
  • 話者の帯（タイムライン）には印を描かない。印のついた発言は文字起こしの側に示す。

ADR-043 多言語対応（日本語・英語）（2026-09）

ADR-043

UI の言語は起動時に macOS の優先言語で決め、会議の言語は文字起こしの言語設定で決める。domain は文言ではなく理由のコードを返し、文言は外側の層が型付きの表から引く

背景

画面・メニュー・通知・エラーの文言が日本語でコードに直接書かれていた（Issue #102）。英語圏にも出すなら、 機能が増えるほど文言を外に出す作業が高くつく。あわせて、文言が src/domain や src/application にもあり（エラーの文、話者の既定名、要約・チャットのプロンプト）、 ステップの失敗は日本語の文のまま meta.json に保存されていた。

UI の言語と会議の言語は別物である。英語 UI で日本語の会議を録る人もいれば、その逆もある。 要約のプロンプトや話者の既定名は録った会議に合わせるべきで、画面の言語から推してはいけない。

決定

  • UI の言語は日本語と英語。main が起動時に app.getPreferredSystemLanguages() を先頭から見て、最初に対応している言語を採る（macOS が Bundle の .lproj を選ぶ規則と同じ）。 どれにも当たらなければ英語。アプリの中では切り替えず、言語を変えたら再起動で反映する。 renderer へは起動引数（--omr-locale）、ワーカーへは環境変数 OMR_UI_LOCALE で渡す。 開発中に別の言語の画面を確かめるときは OMR_LOCALE=en で上書きできる。
  • 文言の表はライブラリを使わず、型付きの自前の表にする。領域ごとに ja と en を並べ、const en: typeof ja と書いてキーの書き忘れ・余分を型検査で落とす。 語順や単複が変わる文は関数にする。main 専用は src/main/i18n.ts、renderer 専用は src/renderer/i18n/、両方で使うもの（失敗の理由・モデル名・ステップ名）は src/shared/i18n/ に置く。
  • domain・application・infrastructure は文言を持たない。失敗は ErrorReason（コードと表示に要る値）を持つ AppError で投げ、message にはコードだけを入れる。文言は main が IPC で返す直前、または renderer が表示するときに UI の言語で引く。 ワーカーは UI の言語を知らなくてよいよう、失敗を理由のまま main へ運ぶ。
  • ステップの失敗は meta.json に文言ではなく理由を保存する（StepState.reason）。 ADR-035 の「項目の追加」なのでスキーマ番号は上げない。error には理由のコード、 理由の無い失敗（ネイティブ由来など）は元のメッセージを残す。知らないコード（新しい版が保存した理由）や 以前の版が保存した日本語の文は、error をそのまま表示する。
  • 会議の言語は文字起こしの言語設定が ja / en ならそれ、 auto などプロンプトを用意していない値なら UI の言語にする。これで次を決める: 要約プロンプト、話者の既定名（自分／参加者A と Me／Participant A）、要約に渡すメモと印の見出し、 whisper に渡す用語集の区切り（読点かカンマか）。
  • 要約プロンプトは設定に全文で保存されていて、既定かどうかの印が無い。同梱の既定プロンプト（どの言語のものでも）と 一致すれば「利用者が書いていない」とみなし、会議の言語の既定に差し替える。書き換えたプロンプトは言語が違っても書いたとおりに使う。 （この全文の一致による判定は、既定の文面を変えると崩れるため ADR-047 で promptMode に置き換えた。 今は promptMode を持たない設定を読み替えるときだけに使う。）
  • 話者の既定名は、どの言語の採番（参加者A / Participant A）も既定とみなす。言語を変えて話者識別をやり直したとき、 前の言語の採番を利用者が付けた名前と取り違えると、声紋の引き当て（ADR-031）に譲れなくなる。
  • 新しく入れた人の文字起こしの言語の既定は UI の言語にする。settings.json は全体を保存するので、 一度でも保存した人の言語は OS の言語を変えても動かない。
  • チャットは録音をまたいで答えるので、会議の言語ではなく問いの言語（かなか漢字を含むか）で 指示文と文脈の注記を切り替える。英語の指示文も「文脈だけを根拠にする」「[1] で引用する」という ADR-032 の出力の契約を日本語版と同じに持つ。何を見て答えたかは文言ではなく 期間と件数で返し、画面が UI の言語で組む。
  • 許可ダイアログの文言は、基底の Info.plist（electron-builder.yml の extendInfo）を英語にし、 build/lproj/<言語>.lproj/InfoPlist.strings に言語ごとの文言を置く。 CFBundleDevelopmentRegion を en、electronLanguages を en / ja に絞る （Electron の数十言語の .lproj が残っていると、例えばドイツ語の人に Electron 由来のメニューだけがドイツ語で出る）。 開発用 Electron.app へのパッチも同じ InfoPlist.strings から入れる。
  • IPC の引数検査の失敗（renderer の不具合でしか起きない）は訳さず、英語の開発者向けの文にする。 ただしタイトル・話者名・フォルダ名のように利用者が空欄のまま確定できる値は、入力を促す理由を返して訳す。

選択肢

論点案判定理由
文言の表 i18next などのライブラリ 不採用 キーの取りこぼしを型検査で拾うには追加の設定が要り、依存も増える。扱う言語は 2 つで、単複の切り替え程度は関数で足りる
UI の言語の決め方 設定画面で選ぶ 見送り macOS のアプリの慣習に合わせた。許可ダイアログは OS の言語でしか出せないので、設定で別の言語を選ぶと画面とダイアログが食い違う
UI の言語の決め方 起動中に切り替える 不採用 メニュー・トレイ・通知を作り直す仕組みが要る。OS の言語の変更は頻繁ではなく、再起動で足りる
失敗の保存 main が UI の言語で文にしてから保存する 不採用 OS の言語を変えると過去の失敗だけが元の言語で残る。ワーカーにも UI の言語を持ち込むことになる
会議の言語 UI の言語に従わせる 不採用 英語 UI で日本語の会議を録る人の要約が英語になる
会議の言語 自動判定のときは whisper の判定結果を使う 見送り 判定結果を保存していないので、要約だけを再実行したときに同じ言語にならない。要るなら transcript.json に言語を持たせてから
チャットの言語 会議の言語の設定に従わせる 不採用 チャットは言語の違う録音をまたぐ。利用者が書いた言語で答えるのが自然で、英語の問いに日本語の指示文を渡すと答えも日本語に寄る

残した判断

  • チャットの日付・話者・節の解釈（DateExpression.ts / ChatQuery.ts）と、意味検索の問いの言い回しの除去 （focusQuery）は日本語の言い回しだけを読む。英語の問いでは期間や話者で絞れず、新しい順と意味検索で答える。 英語の言い回しは別に扱う。
  • 意味検索のチャンク長（160 字）は日本語で決めた値で、英語の会議では 1 チャンクに入る語が少なくなる。
  • 文字起こしの評価（npm run eval:transcription）は日本語の合成音声だけ。英語の定型句のブロックリストは完全一致で、 日本語の会議の結果は変わらない。

ADR-044 新しい版の通知（2026-09）

ADR-044

GitHub Releases の latest を設定の間隔（既定は週 1 回）で確かめ、今の版より新しければ入れ方（Homebrew / DMG）に応じた更新の手順を知らせる。アプリは自分を入れ替えず、確かめられなかったことは見せない

背景

一般公開したあと、配った版を使い続ける人に新しい版があることを知らせたい（Issue #98）。通知の仕組みは後から足しても 「足す前の版」の利用者には届かないので、最初の公開版に入れておく必要がある。

一方で、当面は Developer ID を取らず ad-hoc 署名で配る。ad-hoc 署名ではアプリの身元（designated requirement）が cdhash になり、Squirrel.Mac / electron-updater の検証が通らない。アプリ自身による自動更新は使えない。

決定

  • 確認先は GitHub Releases の latest に一本化する。 GET https://api.github.com/repos/eddybean/exolobe/releases/latest を認証なしで引く。 DMG と Homebrew のどちらで入れても同じ Release を配るので、確認先を分けない。latest はドラフトとプレリリースを返さない。
  • 知らせるだけで、アプリは自分を入れ替えない。ナビの右端に「新しい版」の札を出し、押すと設定の 「このアプリについて」で手順を見せる。Homebrew（/opt/homebrew/Caskroom/exolobe か /usr/local/Caskroom/exolobe がある）なら brew update && brew upgrade --cask exolobe を （tap のクローンが古いと upgrade だけでは「既に最新」と返るため update を前に付ける）、 それ以外は配布ページを案内する。Homebrew で入れた人が DMG で上書きすると、brew の記録と実体の版が食い違うため。 cask に auto_updates true は付けない。
  • 間隔は設定で選ぶ（毎日・毎週・毎月・確認しない）。既定は週 1 回。急ぐ知らせではなく、GitHub への問い合わせを 必要以上に増やさない。問い合わせるかどうかはユースケース（CheckForUpdate）が前回の確認 （userData/update-check.json、失っても確かめ直すだけのキャッシュ）と間隔から決める。main は起動の 15 秒後と 1 時間ごとに「時期か」を見るだけで、時期でなければ通信しない。「今すぐ確認」は間隔も「確認しない」も越えて問い合わせる。 読めない設定値は週 1 回に倒す（「確認しない」に倒すと、古い版のまま使い続ける人が残る）。
  • 確かめられなかったことは見せない。404（リポジトリが非公開の間・Release がまだ無い）は「更新なし」として 記録し、間隔まで問い合わせない。通信の失敗・上限超過（403）・サーバーの失敗は記録を変えず、次の見回りで確かめ直す。 どちらも例外にせず、画面にも出さない。知らせるだけの機能で、利用者に打てる手が無いため。
  • 版の比較は domain の純粋関数（AppUpdate.ts）。タグ（v0.3.0）と app.getVersion() を数の組として比べる。どちらかが読めない（プレリリースなど）なら知らせない側に倒す。
  • 配布ページの URL は main だけが持つ。返事の html_url は使わず、検証済みのタグから https://github.com/eddybean/exolobe/releases/tag/… を組む。renderer には版と入れ方だけを渡し、 開く操作は引数なしの IPC にする。記録のファイルに GitHub 以外の URL があれば読まない。
  • プライバシー。GitHub に届くのは IP アドレスと User-Agent（Exolobe/<版>）だけ。 設定の説明と README に、通信の種類と時機をモデルのダウンロードと並べて書く。

選択肢

論点案判定理由
更新の仕方 electron-updater による自動更新 見送り ad-hoc 署名では Squirrel.Mac の検証が通らない。Developer ID を取ればそのまま使えるので、そちらを先に検討する
更新の仕方 自作の差し替え 不採用 配布物の署名検証（Ed25519）、差し替えのスクリプト、App Translocation・書き込み権限・録音中の扱いが要り、知らせるだけに比べて得るものが少ない
知らせ方 macOS の通知センター 不採用 通知は録音の開始忘れ・無音の知らせに使っている。急がない知らせで割り込まず、アプリを開いたときに目に入れば足りる
確認の失敗 画面にエラーを出す 不採用 非公開の間は必ず 404 になる。オフラインの人にも毎回出る。利用者に打てる手が無い

残した判断

  • 実際の Release での確認は、リポジトリを public にした後に行う。非公開の間は常に「更新なし」になる。
  • 更新のたびにプライバシーの許可（マイク・システム音声）が外れる可能性がある。身元が cdhash のため、TCC の許可が ビルドごとに別物として扱われる可能性が高い（未確認）。通知の有無に関係なく既にある問題で、Developer ID の判断材料になる。
  • Homebrew の tap / cask は public 化の後に作る。cask 名は exolobe を前提に判定と案内を書いている。

ADR-045 同梱バイナリの最低対応 OS と CI のランナー（2026-09）

ADR-045

同梱バイナリ（whisper-cli / micwatch / calendarevents）は、アプリが宣言する最低対応 OS（electron-builder.yml の LSMinimumSystemVersion）向けにビルドし、配布前に検査する。そのうえで CI と Release のランナーを xcode-27 に上げる

背景

macOS 27 の Apple Intelligence（FoundationModels）を要約のモデルとして選べるようにしたい。呼び出しは micwatch などと同じく同梱の Swift ツールにするつもりで、そのビルドには macOS 27 SDK が要る。macos-15 の ランナーは SDK が 26.2 までで、コンテキスト長（contextSize、macOS 27 から）もトークン数 （tokenCount、26.4 から）も扱えない。

ランナーを上げる前に調べると、build-*.sh は対象 OS を指定しておらず、swiftc も clang もビルドした機械の OS を 最低対応 OS にしていた。手元の resources/bin は 3 本とも minos 26.0、macOS 27 で作り直すと minos 27.0 になる。アプリは 14.2 以降で動くと宣言しているのに、同梱バイナリはランナーの OS 以降でしか起動しない。 アプリ自体は起動するので、文字起こしが失敗して初めて気付く。macos-15 でビルドした配布版も同じ形の食い違いを持つ（推定）。

決定

  • 最低対応 OS は LSMinimumSystemVersion から読み、二重に持たない。 scripts/min-macos.sh が値を読み、Swift は -target arm64-apple-macos<版>、whisper.cpp は CMAKE_OSX_DEPLOYMENT_TARGET で渡す。既にあるバイナリの minos が違えば作り直す （Core ML 無しの whisper-cli を作り直すのと同じ扱い）。
  • 配布前に検査する。scripts/check-min-macos.sh が同梱バイナリの minos を読み、 最低対応 OS より新しければ Release を止める。キャッシュの whisper-cli はキーに electron-builder.yml を含めない （変更のたびに数分の作り直しになる）ので、最低対応 OS を変えたときの取り残しはこの検査で拾う。
  • ランナーは xcode-27（macOS 27、Xcode 27.0、arm64）。ci.yml と release.yml で揃える （main の CI が作ったキャッシュを Release が読むため）。

確かめたこと

  • 14.2 を指定しても 3 本ともエラーなくビルドでき、minos 14.2 になる。
  • whisper-cli は 14.2 向けにしても Metal・Core ML・bfloat・SME を使い、合成音声の会議で処理時間（約 5.7 秒）と 出力が 26.0 向けのものと同じだった。

選択肢

論点案判定理由
ランナー macos-15 のまま、Swift ツールの段だけ Xcode 26.3 に切り替える 不採用 SDK 26.2 では macOS 27 の API を使えず、コンテキスト長を決め打ちするなど回避の書き方が要る
ランナー macos-26 不採用 SDK が 26.5 までで、上と同じ理由
最低対応 OS ランナーの OS に任せる（今まで） 不採用 ランナーを上げるたびに、宣言より新しい OS でしか動かないバイナリが黙って配られる

ADR-046 要約のモデルに Apple Intelligence を選べる（2026-09）

ADR-046

macOS 27 の Apple Intelligence（FoundationModels）を要約のモデルとして設定で選べるようにする。既定は Gemma のままにし、選んでいる間は精度が劣ることを設定画面に出し続ける

背景

macOS 27 で Apple Intelligence の端末内モデルが強化され、コンテキスト長が 8192 トークンになり、日本語にも対応した。 OS に入っているのでダウンロードが要らず、このアプリのメモリも使わない。一方で、要約の質が Gemma 4 E4B に大きく劣るなら 入れる意味が無いので、先に同じ条件で比べた。

比較（2026-09-28、M4、合成の会議 4 本）

アプリと同じ LlamaCppSummarizer（分割 → 統合、防御の前置き、既定のプロンプト）にモデルだけを差し替え、 どちらも貪欲法で生成した。文字起こしは whisper らしい誤り（同音異義・字幕の定型句・反復）を混ぜた合成で、 評価の道具とデータはリポジトリの外（online-meeting-recorder-eval/summarization）にある。

キーワードでの拾い方はほぼ並ぶが、読むと差ははっきりしている。Apple は決定事項に ToDo や提案を混ぜ、ToDo の期限を 担当者ごとに 1 つへ潰して取り違える。長い会議では部分要約の箇条書きをほぼそのまま並べ（6,658 字。Gemma は 2,541 字）、 概要と議論の流れが同じ文の繰り返しになる。速さは 30 分程度までなら数倍だが、長い会議では部分要約を順に呼ぶぶん Gemma より遅い。

決定

  • 既定は Gemma のまま。Apple Intelligence は選んだ人だけが使う。設定の summarization.provider（元から 'llama-cpp' だけの項目）に 'apple-intelligence' を足す。 知らない値は llama-cpp として読む（ADR-035）。選んでいる間は、精度が劣ることと 長い会議での崩れ方を設定画面に出し続ける。
  • 分割・統合・防御の前置きは共用し、応答の入れ物だけを差し替える。LlamaCppSummarizer の セッションを、同梱の applelm（Swift、native/applelm）を 1 回ずつ起こすものにする。 8192 トークンに履歴を溜めないよう、呼ぶたびに新しいセッションにする。コンテキスト長はジョブの開始時に applelm status から取る。
  • 部分要約が統合の段に収まらなければ、もう一段まとめ直す。8192 トークンでは 2 時間を超える会議で 部分要約の合計が溢れる。縮まなくなったら打ち切り、段数は 3 までにする（Gemma にも同じく効く）。
  • macOS 27 未満では使えないことにする。評価したのは 27 のモデル（26 はコンテキストが 4096）。 applelm は FoundationModels を弱リンクにし、最低対応 OS（14.2）でも起動して unsupported-os を返す。
  • 安全フィルタは permissiveContentTransformations。要約は与えた文章の書き換えで、 既定のフィルタでは会議に普通に出る話題で応答ごと拒まれることがある。拒まれたら理由として保存し、Gemma への切り替えを案内する。
  • Apple Intelligence を選んでいれば、要約前のメモリ見積もりと初回セットアップでの Gemma の要求をしない。 モデルは OS のプロセスで動く。Gemma のパスは消さずに残し、戻したときに取り直させない。
  • チャットは Gemma のまま。ライブラリ全体を文脈に入れるには 8192 トークンは狭い。

ADR-047 要約プロンプトの既定とカスタム（2026-09）

ADR-047

要約プロンプトを「アプリの既定」と「カスタム」から選ぶ形にする。既定は読み取り専用で見せ、どちらを使うかは本文の一致ではなく summarization.promptMode で持つ

背景

要約プロンプトは設定に全文で保存されていて、既定かどうかの印が無かった。ADR-043 は 「同梱の既定の全文と一致すれば利用者が書いていない」とみなして会議の言語の既定に差し替えている。 ところが settings.json は、どの項目を保存しても全体を書き出す。プロンプトに一度も触れていない人の ファイルにも、その時点の既定の全文が入っている。

このため、既定の文面を直した版を出すと、保存済みの古い全文は新しい既定と一致しなくなり、 「書き換えたプロンプト」として扱われる。触っていない人に新しい既定が届かず、会議の言語での切り替えも止まる （英語の会議でも古い日本語の既定で要約する）。{{notes}} を足したとき（ADR-042）に 「無ければ末尾に付ける」を入れたのは、この症状を個別に抑えたものだった。既定の文面を育てるたびに同じことを踏む。

決定

  • どちらを使うかを summarization.promptMode（'default' / 'custom'）で持つ。 既定なら要約の実行時に会議の言語の既定を引き、保存されている本文は見ない。カスタムなら promptTemplate を書いたとおりに使う。 知らない値（新しい版が足したもの）は既定として使う。
  • 既定は編集させない。設定画面は「アプリの既定 / カスタム」の選択にし、既定のときは本文を読み取り専用で見せる。 書き換えたいときはカスタムを選ぶと、今の既定の写しから編集を始められる。
  • カスタムの本文は、既定に切り替えても消さない。カスタムに戻したら続きから書ける。 {{transcript}} の検証はカスタムのときだけ行う（既定の間は本文を要約に使わないため）。
  • promptMode を持たない設定は、読み込み時にこれまでの判定で読み替える。 本文が既定の全文と一致すれば既定、そうでなければカスタム。既定値の 'default' で補うと、 書き換えた人の要約が黙って既定に戻る。項目の追加なので schemaVersion は上げない（ADR-035）。
  • promptTemplate の型と意味は変えない。前の版は promptMode を知らず本文だけを読む。 新しく入れた人の本文には既定の全文を入れておき、前の版に戻しても「既定のまま」と読まれるようにする。

選択肢

案判定理由
全文の一致で見分けるのを続け、既定を変えるたびに旧版の全文を「既定」の一覧に足す 不採用 過去の全文を持ち続けることになり、1 つ漏らすと触っていない人が黙って取り残される
promptTemplate を string | null にし、null を既定とする 不採用 前の版が null を読むと文字列として扱えずに落ちる。型を変えるなら形式の番号を上げることになる
名前付きのプロンプトを複数持ち、そこから選ぶ 見送り 設定で 1 つを選ぶだけなら、得られるのは「既定を壊さない」ことだけで、それは本案で足りる。 録音ごと（または要約のやり直しで）プロンプトを選べるようにするときに、カスタムを複数に広げる

残した判断

  • カスタムを選んでから既定に戻した人が前の版に戻すと、前の版は残っているカスタムの本文で要約する。 版を戻すことはまれで、本文を消して防ぐとカスタムに戻したときの続きが失われるので、こちらを取る。
  • カスタムの人には、既定の改善は届かない。どちらを選んでいるかは設定画面に出ていて、既定の本文もそこで読める。

ADR-048 Windows 対応（2026-10）

ADR-048

Windows 版を作る。OS ごとに別のインストーラにし、OS の違いは結線（container）で実装を選んで吸収する。domain と application には OS の分岐を持ち込まない

背景

録音・文字起こし・話者識別・要約をローカルで行う作りは Windows でも成り立つ。文字起こし以降の推論は port の裏にあり、 sherpa-onnx-node と node-llama-cpp は Windows 向けのビルド済みパッケージを持つ。 一方で、音声の入出力（audiotee・afconvert）と OS との連携（権限・通知・メニュー・同梱の Swift 製補助プログラム）は macOS にしか無い。いくつかは port を通さず、IPC のハンドラから Electron の API や OS のコマンドを直接呼んでいた。 開発の道具（postinstall の bash、実際の afconvert を呼ぶテスト、xcode-27 だけの CI）も macOS が前提で、Windows では npm ci から通らなかった。

決定

  • OS ごとに別のインストーラにする。macOS は dmg、Windows は NSIS。同梱バイナリは mac / win の extraResources に分け、互いの配布物に混ぜない。ネイティブモジュールは npm がその OS の分だけ入れるので、ビルドはそれぞれの OS の CI で行う（クロスビルドしない）。
  • OS の違いは結線で吸収する。どの実装を使うかを決めるのは container.ts とワーカーの container だけにし、 domain・application は OS を知らない。直接呼んでいたもの（マイクの権限、システム設定を開く、アーカイブの展開、 インストール元の判定）は port に切り出す。renderer には OS を preload から渡し、ショートカットの表記・フォント・ 文言の出し分けに使う。文言は ADR-043 の表で OS ごとに持つ。
  • 音声の変換は Windows 標準の Media Foundation で行う。ffmpeg は同梱しない。 ADR-030 と同じく「取り込める形式は OS の変換器が読めるもの」とし、取り込める拡張子の一覧は OS ごとに持つ。 HE-AAC は Windows の標準のエンコーダで使えない見込みなので、Windows では AAC-LC だけを選べるようにする （ADR-005 の既定は macOS でも変えない）。
  • Windows 用の補助プログラムは Rust（windows crate）で書く。システム音声のキャプチャ（WASAPI loopback）、 音声の変換、マイク使用の見張りを、Swift 製と同じく stdout で話す単体の exe にする。ランタイムが要らず、 既存の取り決め（audiotee の PCM、micwatch の 1/0）をそのまま守れば TypeScript 側の実装を共用できる。
  • GPU は Vulkan を使う。whisper-cli は Vulkan と CPU でビルドし、node-llama-cpp の CUDA 版は同梱しない （数百 MB あり、Vulkan なら NVIDIA・AMD・Intel のどれでも動く）。Core ML のエンコーダは macOS だけの資産とし、Windows では取得させない。
  • 最初の版は x64・署名なし・カレンダー連携なし。署名しないと SmartScreen が警告を出すが、 ADR-014 の ad-hoc 署名と同じ扱いにする。カレンダー連携が無いので、録音の自動開始 （ADR-041）も Windows では働かない。Apple Intelligence（ADR-046）は選択肢に出さない。
  • 進め方は「macOS で抽象化し、Windows で実装する」。まず Windows の CI で typecheck / lint / fmt / test / build を 通るようにし（実際の OS のコマンドを呼ぶテストはその OS だけで走らせる）、次に OS の違いを結線の裏に寄せる。ここまでは macOS で Fake を使って進められる。ネイティブの補助プログラムと実機での確認は Windows で行う。

選択肢

論点案判定理由
音声の変換 ffmpeg を同梱する 不採用 取り込める形式は増えるが、配布物が数十 MB 増え、ライセンス表示も要る。macOS と同じく OS の変換器に任せれば同梱物が増えない
補助プログラムの言語 C++ / C#（NativeAOT） 不採用 C++ は WASAPI の扱いが冗長で、メモリの誤りを起こしやすい。C# は単体 exe にすると大きく、COM の扱いも Rust の windows crate より手間
補助プログラムの形 Node のネイティブアドオンにする 不採用 Electron の版ごとにビルドし直しが要り、落ちると main プロセスごと落ちる。子プロセスなら隔離され、macOS と同じ作りで扱える
カレンダー連携 Microsoft Graph / Outlook COM 見送り Windows には EventKit のようにローカルで完結する口が無い。Graph はクラウドへのサインインが要り（ADR-003 と相容れない）、新しい Outlook には COM が無い
GPU CUDA 版も同梱する 不採用 NVIDIA でしか効かないのに配布物が数百 MB 増える。速さが足りないと分かってから任意ダウンロードを考える

残した判断

  • メモリの見積もり（ADR-024）の係数は Mac の統合メモリで測った値。Windows の VRAM が別にある機体では合わないので、実機で測り直す。
  • 文字起こしの評価は macOS の say で音声を作っている。Windows では録音済みの音声（OMR_EVAL_EXTRA_DIR）で測る。
  • 新しい版の通知（ADR-044）は OS 共通の Release を見るので、片方の OS だけの修正版でも両方に知らせる。
  • 録音の保存と取り込みは Media Foundation（補助プログラム audioconv）で行う。Windows 11 の AAC エンコーダは サンプルレートごとに使えるビットレートが決まっていて（16kHz は 12〜32kbps、44.1k/48k は 48kbps 以上、8kHz は不可）、 同じ組み合わせで HE-AAC の候補も混ざる。エンコーダに出せる形式を問い合わせ、AAC-LC の中から指定に一番近いものを選ぶ。 扱えないレートは近いレートに変えて保存する。macOS から持ち込んだ設定の HE-AAC は、保存を止めずに AAC-LC で保存する。 変換とチャンネルの混ぜ合わせは Source Reader に任せた（左右に別の音を入れたステレオで、両方が残ることを確かめた）。 読める形式は afconvert と違い、webm / mkv / mov / wma / avi を読み、ogg / opus / aiff / caf を読まない（実機で確認）。 webm の Opus のように、ストアの拡張機能が入っているかで変わるものもある。
  • 配布は NSIS のインストーラ（exolobe-<版>-x64.exe、約 160MB）。Release は prepare のジョブが先に 1 度だけ作り、macOS と Windows の ジョブは成果物を添付するだけにする（両方が「無ければ作る」をすると競合する）。SHA256SUMS.txt は両方の成果物から最後のジョブがまとめて作る （各ジョブが --clobber で上げると、後から終わった方が先の分を消す）。片方の OS が失敗しても、できた分で作る。署名しないので、 SmartScreen の「詳細情報」→「実行」の手順を Release の本文と README に書く。新しい版の通知（ADR-044）は OS 共通の Release を見るので、 片方の OS だけの修正でも両方に知らせる。どちらの OS にも同じ版の配布物が載るので、更新しても害は無い。 macOS 専用の audiotee は Windows の配布物にも入るが、呼ばれないので残す（electron-builder の win の files は上の files を 置き換えるので、外そうとするとリポジトリが丸ごと入る）。展開した中身は約 590MB で、大きいのは node-llama-cpp の CPU 版（47MB）と Vulkan 版（99MB）。どちらも要るので削らない（exFAT の上では du が実際より大きく出るので、--apparent-size で測る）。
  • 画面・メニュー・トレイ・通知を Windows 11 の実機で見た（2026-10）。ウィンドウは標準の枠で、ナビとも重ならない。メニューバーは出したまま （autoHideMenuBar にしない。録音の操作をメニューからも辿れるようにするため）。Windows では役割のメニューが Electron の既定の英語のまま 出て日英が混ざったので、役割の項目にも UI の言語の名前とアクセスキーを付ける（macOS は OS の訳に任せる）。トレイの待機中のアイコンは テンプレート画像が効かず黒のままで、ダークのタスクバーで見えなかったので、タスクバーの明暗に合わせて白く塗る。左クリックでウィンドウ、 右クリックでメニュー（Windows の慣例）。ウィンドウを閉じても終わらず、二重起動でウィンドウが戻る。通知は Electron 44 が Windows の トーストにもボタンを付けるので、トーストの XML は自前で書かない。書体は和文が Yu Gothic UI、等幅が Consolas で描かれる。
  • 要約・チャット・意味検索（node-llama-cpp）と話者識別（sherpa-onnx-node）を Windows 11（RTX 5090、RAM 64GB）で動かした（2026-10）。 54 分・3 話者の合成会議で、文字起こし・話者識別・要約・エンコードが通り、チャットは引用付きで答え、意味検索も答えた。 ワーカーはジョブの後・使われなくなった後に終わり、VRAM も元に戻る（ADR-008）。声紋の取り出し（enableExternalBuffer = false）も Electron の中で通った。 node-llama-cpp は getLlama に gpu: { type: 'auto', exclude: ['cuda'] } を渡し、CUDA 版のパッケージ（win-x64-cuda / -cuda-ext、約 530MB）と Arm 版は electron-builder の files で配布物から外す。CUDA Toolkit の無い機体では自動選択でも Vulkan になるが、ある機体では開発中だけ CUDA を 選んで配布版と食い違うので、明示して揃える。外した配布物（electron-builder --dir）でも要約とチャットが通った。
  • メモリの見積もり（ADR-024）の係数は変えない。要約と同じ条件（Gemma 4 E4B・32K）で測ると、GPU 無しでは RAM が最大 5.66GB、 Vulkan では RAM 3.27GB と VRAM 4.80GB だった。見積もり（約 7.3GB）は GPU 無しの実測を上回るので「足りないのに走って落ちる」は起きない。 GPU のある機体では RAM を 4GB ほど多めに見るが、VRAM に載り切るかは読み込むまで分からず、載り切らなければ RAM 側に回るため、 多めのまま残す（断られたら理由が出て、メモリ保護をオフにすれば走らせられる）。Windows の空きは os.freemem()（「利用可能」と一致する）で測り、 vm_stat は macOS でだけ読む。
  • マイク使用の見張り（ADR-027）は Rust の micwatch.exe。有効な録音デバイスごとに WASAPI の音声セッションを列挙し、Active なものがあれば 使用中とする。親（main）とその子孫のセッションは除く（renderer や Chromium の音声サービスのマイク使用を数えない）。レジストリの CapabilityAccessManager（LastUsedTimeStop が 0）も候補だったが、どのプロセスかが分からず自分の使用を除けないうえ、落ちたアプリの記録が 使用中のまま残りうるので採らなかった（実機で、木の外の ffmpeg には約 1 秒で 1 を出し、木の中の ffmpeg には反応しないことを確かめた）。 TypeScript 側は stdin を渡さないので、親のプロセスを自分で調べ、親が終わったら終わる。出力の取り決め（1 / 0）は macOS 版と同じ。
  • whisper-cli は whisper.cpp の公式のリリース資産を使わず、自前でビルドする（x64 の Vulkan 版が無く、資産の付いたビルド番号も v1.9.x のタグと同じコミットではない）。バックエンドを DLL に分け（GGML_BACKEND_DL）、実行時に読み込む。Vulkan を静的に組み込むと、 GPU ドライバの無い機体では vulkan-1.dll が無くて whisper-cli.exe 自体が起動しないため。CPU も命令セットごとの DLL を作り、 実行する機体で選ばせる（GGML_CPU_ALL_VARIANTS）。同梱は whisper-cli.exe・whisper.dll・ggml の DLL で約 66MB（大半は ggml-vulkan.dll の 55MB）。 Visual C++ ランタイム（msvcp140 / vcruntime140）は Windows に入っているとは限らないので、DLL を横に置く。 Rust の補助プログラムは単体の exe なので、ランタイムを静的に組み込む。
  • 30 分の日本語（Windows の音声合成で docs の文を読み上げたもの、188 発話）を large-v3-turbo q5_0 で文字起こしした（2026-10、Windows 11）。 Vulkan（RTX 5090）は VAD 有りで 33 秒・無しで 21 秒、CPU（ggml-vulkan.dll を除いた状態、既定の 4 スレッド）は 461 秒・621 秒。 CPU でも実時間の約 4 倍速く、文字誤り率はどちらも 0.04 前後で差が無く、取りこぼしは 0。CPU は 8 スレッドにすると 302 秒になった。 スレッド数の既定（whisper-cli の 4）を変えるかは、要約・メモリの見積もりと一緒に実機で決める。 文字起こしの評価の合成音声は macOS の say で作るので、Windows では手元の録音（OMR_EVAL_EXTRA_DIR）だけで測り、基準は取り直さない。
  • システム音声は WASAPI のプロセス loopback（Windows 10 2004 以降）の除外モードで、main の PID 以下の木（このアプリの音）を除いて録る。 実機で、他のプロセスが鳴らした 1 kHz は振幅 0.48 で入り、除いた木から鳴らした音は背景と同じ水準に収まった。 テスト録音は自分の確認音が入るかで判定するので、そのときだけ除かない。補助プログラムは stdin が閉じたら止まるので、 main が落ちてもパイプが閉じて孤児にならない（Job Object は使わない）。 録音の途中で既定の再生デバイスが変わったとき（ヘッドホンを挿すなど）に追従するかは、まだ確かめていない。
